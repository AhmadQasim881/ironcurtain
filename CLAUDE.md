# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## General Workflow

When asked to find a file or document, ask the user for the path after one failed search attempt rather than spending many tool calls searching.

## Git & Worktrees

When working with git worktrees, always verify the current working directory before making changes. Run `pwd` and confirm the target worktree path before any edits.

## Git Workflow

Always stage and verify all relevant files before committing. Run `git status` before `git commit` to confirm nothing is missing.

## Platform Considerations

When fixing bugs or implementing features for cross-platform code (macOS/Linux/Docker), ensure changes are scoped to the correct platform and do not break other platforms. Always ask if unsure.

## Safe Coding

- **No shell string concatenation.** Never use `child_process.exec()` or build command strings by concatenating/interpolating untrusted values. Always use `spawn()`/`execFile()` with argument arrays so the OS handles escaping. Untrusted values must only appear in the args array, never in the command string itself.
- **Encapsulate risky operations.** Security-critical operations (path resolution, credential handling, Docker command construction) must live in dedicated modules with safe public APIs. Application code should call the safe abstraction, not reimplement the logic inline.
- **Use the existing safe APIs.** Host reads and writes of agent-writable paths: `readUntrustedRegularFile`, `writeFileNoFollowAtomic`, `appendRegularFileNoFollow` (and `readOwnedRegularFile` for trusted artifacts) in `src/hardened-fs.ts`. Untrusted text written to a terminal: `toDisplayText`, `toTerminalKitText`, `escapeTerminalKitMarkup`, and `stripTerminalSequences` for agent prose (`src/terminal/display-sanitize.ts`; widths from `src/terminal/display-width.ts`). Host git on agent-writable repositories: `hardenedGitEnv`, `runGit`, `inspectRepoConfig` (`src/security/git-hardening.ts`). Network destinations an agent can influence: `screenIpLiteral`, `createGuardedLookup`, `isLocalOrMetadataHostname` (`src/net/address-policy.ts`). Files holding secrets: `writePrivateFileAtomicSync` (`src/util/atomic-write.ts`), never `atomicWriteTextSync`; read-modify-writes of state shared across processes: `withFileLockSync` (`src/util/file-lock.ts`). Environments of spawned processes: the allowlists in `src/trusted-process/child-env.ts`.

## Project Overview

IronCurtain is a secure agent runtime that mediates between an AI agent and MCP (Model Context Protocol) servers. Every tool call from the agent passes through a trusted process that evaluates it against policy rules (allow/deny/escalate) before routing to the real MCP server. This is a proof-of-concept implementation.

## Commands

**Development invocation.** When running the CLI from source (without an installed `ironcurtain` binary or after editing TS files without rebuilding), use `tsx src/cli.ts <subcommand> ...` — this runs the TypeScript entry point directly. Do NOT use `node dist/cli.js` after editing source unless you've rebuilt; do NOT use `tsx src/index.ts` (that's a different entry that spawns the agent). Examples: `tsx src/cli.ts workflow lint <path>`, `tsx src/cli.ts workflow list`. Every command takes `--help` (`ironcurtain <command> --help`). `start -w .` (or a workflow `--workspace`) pointing at the IronCurtain checkout that is running is rejected, because it contains the package config directory; develop IronCurtain with IronCurtain from a separate checkout.

**Credentials.** Besides the shell environment (which wins) and the key fields of `~/.ironcurtain/config.json`, API keys come only from env files: `~/.ironcurtain/.env` (`$IRONCURTAIN_HOME/.env`), the file given by `ironcurtain --env-file <path> <command>` (the flag goes before the command), or the file named by `IRONCURTAIN_ENV_FILE` (absolute path); only credential names are loaded from them (see `src/config/trusted-env.ts`). A `.env` in the working directory, the repository root included, is never read by the CLI or the npm scripts. The LLM integration tests that `import 'dotenv/config'` still read the repository `.env`.

## Architecture

IronCurtain has two session modes. **Code Mode** (builtin agent) runs LLM-generated TypeScript in a V8 sandbox - IronCurtain controls the agent, the sandbox, and the policy engine. **Docker Agent Mode** runs an external agent (Claude Code, Goose, Codex) in a Docker container with `--network=none` - IronCurtain doesn't control the agent, it only mediates external access through host-side proxies.

### Code Mode: Agent (`src/session/agent-session.ts`, `src/session/prompts.ts`)

`AgentSession` (`agent-session.ts`, created through `createSession()` in `src/session/index.ts`) runs the agent loop: `sendMessage()` calls the Vercel AI SDK v6 (`ai` package) `generateText()` with the session's model and the tools from `buildTools()`, a single `execute_code` tool that sends TypeScript to the Code Mode sandbox. The system prompt comes from `buildSystemPrompt()` in `prompts.ts`. Uses `stepCountIs()` for loop control (not `maxSteps`). The AI SDK v6 API uses `inputSchema` (not `parameters`), `stopWhen` (not `maxSteps`), and `toolCalls[].input` (not `.args`). Anthropic requests carry four prompt-cache breakpoints (`prompt-cache.ts`). Other per-session helpers live beside it: history compaction (`message-compactor.ts`, `tool-result-trimmer.ts`), the per-turn loop detector (`step-loop-detector.ts`) and the conversation saved for `start --resume` (`conversation-store.ts`). Integration tests drive the trusted process directly through `TrustedProcess` (`src/trusted-process/index.ts`).

### Code Mode: Sandbox (`src/sandbox/`)

UTCP Code Mode (`@utcp/code-mode`) provides a V8-isolated TypeScript execution environment. The LLM writes TypeScript that calls typed function stubs (e.g., `filesystem.read_file({path: '...'})`). A custom UTCP `CommunicationProtocol` (`ironcurtain-protocol.ts`) routes tool calls in-process to the `ToolCallCoordinator` for policy evaluation before forwarding to backend MCP servers. Requires `@utcp/mcp` to be imported for the MCP call template type. Tool functions inside the sandbox are **synchronous** (no `await` needed; the script itself runs as an async function body). Each `execute_code` script runs through `code-mode-chain.ts` (an MPL-2.0 copy of the fork's `callToolChain`) under the limits in `chain-limits.ts` (isolate memory, console output, concurrent and queued scripts per sandbox, a process-wide isolate budget). `Sandbox.executeCode(code, { signal, timeoutMs })` cancels the script and withdraws its pending escalations when the signal aborts. MCP relays connect concurrently (`RELAY_CONNECT_CONCURRENCY`), and a server whose relay fails is skipped and reported (`Sandbox.getUnavailableServers`).

### Trusted Process (`src/trusted-process/`)

The security kernel. The `ToolCallCoordinator` (`tool-call-coordinator.ts`) centralizes PolicyEngine (two-phase default-deny evaluation), AuditLog, CallCircuitBreaker, ApprovalWhitelist, AutoApprover, and ServerContextMap as single instances in the Sandbox/CodeModeProxy layer. The security pipeline (`tool-call-pipeline.ts`) contains `handleCallTool` and all policy evaluation, escalation, audit, and argument normalization logic. MCP proxy server subprocesses (`mcp-proxy-server.ts`) are pure relay transports — they forward calls to backends without policy evaluation (they do restart a roots-confined filesystem server under a new OS sandbox profile when its roots change). The set of relays spawned per session is policy-derived: `extractRequiredServers(compiledPolicy)` walks `rule.if.server` and the standalone session path / workflow factory drop everything else from `mcpServers` before `connectBackendSubprocesses` (`src/sandbox/index.ts`) runs (default-deny would reject every call to an unreferenced server anyway). In workflow shared-container mode the coordinator also runs an HTTP control server (`control-server.ts`) on a Unix domain socket for policy hot-swap between agent states; audit entries carry a `persona` field set from the coordinator's `currentPersona`. The workflow factory passes the per-scope union of required servers across all personas with that `containerScope`, so a hot-swap never needs a server that was not spawned.

Further invariants, each detailed in [`src/trusted-process/CLAUDE.md`](src/trusted-process/CLAUDE.md): audit failures fail closed (a write-ahead `dispatching` record precedes every dispatch, and a failed audit write refuses all later calls; readers filter with `isDispatchingAuditEntry` from `src/types/audit.ts`); a call carrying an argument its annotation does not list is denied (`unannotated-arguments`); an argument with a policy role (any role but `none`) that holds a nested object or array escalates human-only (`structural-nested-argument-escalate`); the domain gate resolves git remotes in-process, never running git in the agent's repository; escalation waits are bounded by `escalationTimeoutSeconds` and are cancelled on `close()`, policy hot-swap or when the calling script ends. Opt-in layers: the task scope (`--task-scoped`, intersected with the session policy), taint escalation (`taintEscalation.enabled`: after untrusted content is read, outbound sink calls need a human; `AuditEntry.taint` records it), outbound content assessment (`contentAssessment`, the `assess` rule outcome), MITM egress policy (`egressPolicy`, the virtual `network` server), and the read-only workspace of reviewer workflow states (`structural-read-only-workspace`). Workflow agent states report results through the coordinator-owned `workflow_commit` tool (virtual `workflow` server).

### Policy Compilation Pipeline (`src/pipeline/`)

Two-command offline pipeline (`annotate-tools` + `compile-policy`) that produces generated artifacts with content-hash caching, verification-gated per-server caches, a deterministic policy lint, and dynamic list resolution. See [`src/pipeline/CLAUDE.md`](src/pipeline/CLAUDE.md) for details.

### Session (`src/session/`)

**ResourceBudgetTracker** (`resource-budget-tracker.ts`) - Code Mode budgets. All four limits (tokens, steps, wall-clock time, estimated cost) are **per turn**: they reset when the agent returns control, and idle time between turns does not count. Every AI SDK step is recorded and priced from `onStepFinish` (list prices in `src/llm-metrics/pricing.ts`, overridable per model with `resourceBudget.modelPricing`); the `stopWhen` condition only reads the tracker. Three enforcement points: StopCondition (between agent steps), AbortSignal (wall-clock timeout), pre-check in `execute_code`. Any exhausted dimension ends the turn with `BudgetExhaustedError` (code `BUDGET_EXHAUSTED`); the turn's steps stay in the history with "Stopped after N steps without a final answer". The step cap is `resourceBudget.maxSteps`, or `STEP_SAFETY_CAP` (1000) when that is null. `BudgetStatus` carries the current turn plus `lastTurn` and `cumulative`; code that reports after a turn has ended must read those. Configured via `resourceBudget` field in `~/.ironcurtain/config.json` (all fields nullable to disable individual limits). Defaults: 1M tokens, 200 steps, 30min, $5. Docker Agent Mode applies the same limits differently: `maxSessionSeconds` bounds each container turn (enforced inside the container, `src/docker/turn-timeout.ts`); `maxTotalTokens` and `maxEstimatedCostUsd` are cumulative per Docker bundle and enforced mid-turn at the MITM by the budget gate (`src/docker/budget-gate.ts`; for PTY/mux sessions the cap covers the whole session); and cumulative tokens, turns and cost are checked before every turn (`budget-admission.ts`). Where the agent model and limits come from (CLI flag, workflow state, persona, global config) is defined in one place, `model-budget-precedence.ts`.

Escalations: `Session.getPendingEscalations()` returns every pending escalation (oldest first) and `onEscalationExpired` receives the escalation id; the CLI decides them with `/approve [N]`, `/approve+ [N]`, `/approve+dir [N]` and `/deny [N]` (a bare command is refused while more than one is pending). Logging: `logger.setup()` returns a claim, released with `logger.release(claim)`; work is bound to a claim with `logger.runWithClaim(claim, fn)` (sessions log to their own `session.log`; the daemon's and Signal bot's claims are process-wide), and `logger.teardown()` is only for process exit and tests.

### Docker Agent Mode (`src/docker/`)

Runs external agents in Docker containers with `--network=none`, communicating via UDS-mounted MITM and MCP proxies. The container backend is pluggable (`ContainerRuntime` interface): Docker, or Apple `container` (macOS 26+, Apple silicon, VM per container, `container` >= 1.2.1), which uses the same `uds` topology with each proxy socket file mounted individually (`-v`, vsock relays) and `--network none`; only macOS Docker Desktop uses the TCP sidecar (`src/docker/network-topology.ts`). The runtime is selected by the `containerRuntime` config field (`auto` default) or the `IRONCURTAIN_CONTAINER_RUNTIME` env override. See `docs/designs/apple-container-runtime.md`. Real credentials (API keys or OAuth tokens) never enter the container - fake sentinel keys are swapped host-side, any other credential gets a local 401, and request sanitizers strip provider-hosted tools from completion requests. OAuth is auto-detected from `~/.claude/.credentials.json` and preferred over API keys. Agents keep passwordless sudo unless `agentSudo` is false, and on Linux Docker IronCurtain refuses to run as root. The `DockerInfrastructure` bundle has two lifecycles: standalone sessions own their bundle (`ownsInfra: true`) and destroy it on `close()`, while workflow shared-container sessions borrow the orchestrator's bundle (`ownsInfra: false`) via `SessionOptions.workflowInfrastructure`. `DockerProxy.getPolicySwapTarget()` is the narrow seam the orchestrator uses to attach a control server to the sandbox's coordinator. Passthrough domains (`add_proxy_domain`, human-only) are approved per `host:port` and SNI-pinned. Opt-in **token-trajectory capture** (`--capture-traces`) records the verbatim agent↔provider exchanges at the MITM as per-session JSONL for SFT/RL training data — off by default, zero-cost when disabled; see [`TRAJECTORIES.md`](TRAJECTORIES.md). See [`src/docker/CLAUDE.md`](src/docker/CLAUDE.md) for details.

### Workflows (`src/workflow/`)

The orchestrator runs workflow definitions as state machines; see [`WORKFLOWS.md`](WORKFLOWS.md). Its `AgentSlotPool` (`agent-slot-pool.ts`) caps concurrent agent environments (`maxConcurrentAgentSessions`, daemon-wide under the daemon). A run waiting at a human gate while it holds a shared container is stopped resumably after the gate idle timeout (`gateIdleTimeoutMinutes`, default 4 hours), releasing its containers; `workflow resume` raises the same gate again. Sessions that borrow a workflow shared-container bundle never run a memory server.

### Google Workspace OAuth Token Lifecycle

The Google Workspace MCP server (`@alanse/mcp-server-google-workspace`) intentionally does **not** receive a refresh token. The credential file (`gworkspace-credentials.ts`) omits `refresh_token` to prevent the MCP server from independently refreshing tokens, which would cause refresh token rotation races. Instead, the proxy's `TokenFileRefresher` (`token-file-refresher.ts`) proactively refreshes the access token and rewrites the credential file before expiry. The MCP server re-reads the credential file on each tool call via `loadCredentialsQuietly()`, picking up the refreshed token transparently. The refresh lifecycle: `OAuthTokenProvider` (in `src/auth/`) holds the refresh token and calls Google's token endpoint; `TokenFileRefresher` checks every 5 minutes and force-refreshes via `OAuthTokenProvider.forceRefresh()` when within 10 minutes of expiry (bypassing the provider's normal 5-minute buffer); `writeGWorkspaceCredentialFile()` atomically writes the new access token.

### Configuration (`src/config/`)

**Interactive Config Editor** (`config-command.ts`) - `ironcurtain config` subcommand. Uses `@clack/prompts` for a terminal UI to view and modify `~/.ironcurtain/config.json`. Covers models, security settings (escalation timeout, auto-approve, OS sandbox policy, stale policies, LLM interaction log, agent sudo, taint escalation, outbound content checks), resource limits, auto-compaction, web search, model provider profiles, MCP server credentials, memory, LLM statistics, container snapshots, session mode and the Docker agent. The provider API keys themselves are not in the menu (use the credential files below or edit config.json). Changes are tracked as a partial `UserConfig`, diffed against the resolved config, and saved via `saveUserConfig()`.

**Credentials and home.** Every entry point first calls `bootstrapTrustedEnvForProcess()` (`src/config/trusted-env.ts`): only credential keys are loaded from the trusted env files, never from a working-directory `.env`. `IRONCURTAIN_HOME` (default `~/.ironcurtain`; empty means the default) and `IRONCURTAIN_ENV_FILE` must be absolute paths.

`loadConfig()` reads `AUDIT_LOG_PATH` and `ALLOWED_DIRECTORY` from the environment (provider keys arrive through `loadUserConfig()`) and the MCP server definitions from `loadMcpServers()` (`src/config/mcp-servers-overlay.ts`: the package's `src/config/mcp-servers.json` with the user's `~/.ironcurtain/mcp-servers.json` layered over it, schema-validated, reserved names refused). The `ALLOWED_DIRECTORY` defines the sandbox boundary for policy evaluation. In multi-turn sessions, each session gets its own sandbox at `~/.ironcurtain/sessions/{sessionId}/sandbox/`. When `--workspace <path>` is provided, the validated workspace replaces the session sandbox as `allowedDirectory` (see `src/session/workspace-validation.ts`: the workspace may not be, contain or lie inside the IronCurtain home (apart from its managed workspaces), the package config directory or a protected path, and may not be or contain the user's home; containment is judged by file identity). The fallback default is `$IRONCURTAIN_HOME/sandbox`. Workflow runs live under `~/.ironcurtain/workflow-runs/<workflowId>/` instead of the per-session tree (see [`WORKFLOWS.md`](WORKFLOWS.md) for the layout). Completed runs retain their `checkpoint.json` for post-hoc inspection; see `src/workflow/workflow-discovery.ts` for the unified directory-scan utility consumed by both the CLI `workflow inspect` command and the daemon's past-runs UI. `applyAllowedDirectoryToMcpArgs()` in `src/config/index.ts` is the single source of truth for keeping `mcpServers.filesystem.args` in sync with the active `allowedDirectory`; session, workflow factory, and pipeline all call it. `applyReadOnlyWorkspace()` (`src/config/read-only-workspace.ts`) is the single place a session or workflow bundle becomes read-only. `validatePolicyDir()` in `src/config/validate-policy-dir.ts` realpath-resolves candidate policy directories and accepts only the exact compiled-policy directories (`<home>/generated`, `<home>/personas/<name>/generated`, `<home>/jobs/<id>/generated`, `<home>/task-policies/<key>`, the package's `generated/` and `generated-readonly/`), with owner and mode checks up the directory chain; policy artifacts are then read without following symlinks (`readOwnedRegularFile`). `loadGeneratedPolicy()` loads compiled artifacts (`compiled-policy.json`, `tool-annotations.json` with the user overlay layered per server, and optionally `dynamic-lists.json`) from `~/.ironcurtain/generated/` when present, falling back to the package's `src/config/generated/`; every artifact is schema-validated (`src/types/policy-schema.ts`, code `POLICY_ARTIFACT_INVALID`), and a policy whose `provenance` no longer matches the running IronCurtain (`src/policy-artifacts/`) is reported or refused according to `policy.onStale` (`warn` by default, or `refuse`). `buildSessionConfig` refuses a persona or job policy directory without a compiled policy instead of falling back to the package policy. The OS sandbox policy (`sandboxPolicy`: `enforce` by default on Linux and macOS, or `warn`) is resolved in `src/config/sandbox-policy.ts`, and `ironcurtain doctor` checks the OS sandbox (bubblewrap, socat and ripgrep on Linux, plus a sandbox-runtime smoke run). The `retention` block drives `ironcurtain prune` (`src/maintenance/`; `retention.autoPrune` makes the daemon prune daily).

Memory is enabled per-persona / per-job; toggle at creation time or via `ironcurtain persona edit` / `ironcurtain daemon edit-job`. The global kill switch lives at `ironcurtain config -> Memory -> Enabled` (default on); when off, memory is disabled for every session regardless of per-persona/per-job state. The decision is centralized in `isMemoryEnabledFor` (`src/memory/memory-policy.ts`; a borrowed workflow bundle always means off) with a loader-aware variant `isMemoryEnabledForPersonaName` (`src/persona/memory-gate.ts`) used by the workflow orchestrator when only a persona name is in scope. Memory servers keep their pinned, hash-verified models in `~/.ironcurtain/models` (`src/memory/memory-models.ts`); IronCurtain never passes `MEMORY_MODEL_MANIFEST`, so the servers it spawns use the built-in pins. Unattended writers (cron jobs, workflows) are identified to the memory server (`MEMORY_WRITER_KIND`, `MEMORY_WRITER_SCOPE` from `cronMemoryScope`/`workflowMemoryScope` in `src/memory/memory-annotations.ts`), and what they write waits for review (`ironcurtain memory <name> review`). Which API key may reach the memory server's LLM endpoint is decided in `src/memory/memory-llm.ts`.

### Web UI (`src/web-ui/` + `packages/web-ui/`)

Opt-in Svelte 5 SPA served by the daemon via `--web-ui`. The daemon starts an HTTP+WS server (default `127.0.0.1:7400`) that serves compiled static assets and handles a JSON-RPC WebSocket protocol with bearer token auth. The server rejects a `Host` that is not localhost, loopback or the bind host at the listening port (421), checks the WebSocket `Origin` the same way (plus the Vite origins with `--web-ui-dev`), and sends a strict CSP with `Referrer-Policy: no-referrer`. Backend modules: `WebUiServer` (HTTP/WS lifecycle), `json-rpc-dispatch` (a thin router over the per-domain modules in `src/web-ui/dispatch/`, with Zod validation; the method names are the `MethodName` union in `web-ui-types.ts`), `WebEventBus` (typed pub/sub), `WebSessionTransport` (follows `SignalSessionTransport` pattern). The frontend is a workspace package at `packages/web-ui/` built with Vite + Tailwind v3. Views: Dashboard, Statistics, Sessions, Escalations, Jobs, Workflows (with a per-run WorkflowDetail view), Personas and Settings; markdown (workflow artifacts, message logs, persona constitutions, workflow READMEs) is rendered with a strict `marked` + DOMPurify profile. For development with hot reload: run `ironcurtain daemon --web-ui --web-ui-dev` in one terminal and `cd packages/web-ui && npm run dev` in another — Vite's dev server proxies `/ws` to the daemon. In **Docker Agent Mode** a session is a live terminal (`source.kind === 'web-pty'`): `PtySessionManager` (`src/web-ui/pty-session-manager.ts`) spawns the same `ironcurtain start --pty` child that `mux` uses, wrapped in the shared `PtyBridge` (`src/pty/`), and streams `session.pty_replay`/`pty_output` frames (base64) over the existing WS, mediating input via `sessions.pty*` methods. PTY sessions live outside `SessionManager` (they are not turn-based) but reuse its label allocator. In Code Mode the daemon still creates turn-based sessions (`sessions.send`), but the SPA has no chat view for them and shows them as an unsupported session type. Every turn-based web session ends through `endManagedSession` (`src/web-ui/web-session-teardown.ts`), which emits exactly one `session.ended`; PTY escalations still pending when the child exits are expired (`escalation.expired`) before it. See [`packages/web-ui/CLAUDE.md`](packages/web-ui/CLAUDE.md) ("PTY terminal streaming") and [`docs/designs/webui-pty-terminal.md`](docs/designs/webui-pty-terminal.md).

### Types (`src/types/`)

Shared types: `ToolCallRequest`/`ToolCallResult`/`PolicyDecision` in `mcp.ts`, `AuditEntry` in `audit.ts`. Policy decisions have three outcomes: `allow`, `deny`, `escalate`. The compiler model emits only `allow` and `escalate` rules; `applyOutboundAssessment` (`src/trusted-process/outbound-rules.ts`) turns an allow that can match an outbound-channel tool into `assess` (an allow subject to the opt-in outbound content assessment). The rule schema also accepts `deny` (hand-written policies), and `deny` is the default fallthrough when no rule matches.

## Onboarding a New MCP Server

Users add servers without touching the package: `ironcurtain mcp add <name> ...` writes `~/.ironcurtain/mcp-servers.json`, annotates the server and compiles its rules. Path, URL and identifier roles are restricted to the built-in servers whose semantics they describe (`serverNames`), so a user-added server gets only `none` roles and policy cannot inspect its arguments; `mcp add` and `mcp remove` also drop a reused name's rules from every compiled policy (global, persona, job). Adding a server to the package itself (developer flow) requires changes across configuration, policy, and tests:

1. **`src/config/mcp-servers.json`** — Add server entry with `command`, `args`, and `sandbox` config. Pin the server exactly (an exact npm version, or a container image by digest). For Docker-based servers, use `"sandbox": false` (Docker provides isolation). A server that reopens validated paths by name (like the filesystem server) needs `sandbox.filesystem.confineToRoots`. Credential env vars use `-e VAR_NAME` (no `=value`) so Docker forwards from the host environment.
2. **`src/config/user-config.ts`** / **`src/config/config-command.ts`** — If the server needs credentials (API tokens), add a `SERVER_CREDENTIAL_HINTS` entry in `config-command.ts` for guided setup, and add a prompt step in `first-start.ts`. Credentials go in `serverCredentials.<serverName>.<ENV_VAR>` in `~/.ironcurtain/config.json`.
3. **`src/types/argument-roles.ts`** — Extend `serverNames` on any existing roles that apply to the new server (e.g., `branch-name` for GitHub). Add new roles only if the server introduces new resource-identifier semantics.
4. **`src/config/constitution.md`** — Add guiding principles for the new server's tools (e.g., read-only operations are safe, mutations require approval).
5. **`src/pipeline/handwritten-scenarios.ts`** — Add ground-truth scenarios for critical policy decisions involving the new server.
6. **`test/fixtures/test-policy.ts`** — Add representative tools to `testToolAnnotations.servers` and corresponding rules to `testCompiledPolicy.rules`. Each tool needs an `inputSchema` (use `objectSchema`) declaring exactly its arguments; `test/test-policy-fixture.test.ts` enforces this.
7. **`test/policy-engine.test.ts`** — Add unit tests verifying the new server's tools are correctly allowed/escalated/denied.
8. **Run the pipeline** — `npm run annotate-tools -- --server <name>` (writes the new server into your user overlay), review it, promote it into the package with `npx tsx scripts/stamp-package-annotations.ts --from ~/.ironcurtain/generated/tool-annotations.json --server <name>`, then `npm run compile-policy` (compiles policy rules). Use `--all` instead of `--server` to re-annotate all servers. `annotate-tools --all` skips a server that fails to connect (e.g., Docker not available) with a warning and keeps its previous annotations; a server whose annotation fails also keeps them, and the run exits 1 naming it. `compile-policy` validates the scenarios of an unreachable server against the stored schemas. Every argument the live server exposes must be annotated: a call using an argument the annotation does not list is denied (`unannotated-arguments`). After bumping a server's version, run `npm test` (`annotation-drift.integration.test.ts`) or `ironcurtain annotate-tools --check`, then re-annotate and promote.

## Publishing / Workspace Dependencies

This is an npm workspaces monorepo (`"workspaces": ["packages/*"]` in the root `package.json`). **Do not use `workspace:*`** for workspace package references — that protocol is pnpm-specific and breaks `npm install -g`. Instead, use a normal semver range (e.g., `"^0.1.3"`) pointing at the published version. npm workspaces will still resolve it to the local package during development, and `npm install` from the registry will pull the published version.

When bumping a workspace package version, remember to update the corresponding dependency range in the root `package.json`.

## Validating Policy Engine and Tool Annotations

Quick validation of compiled policies and annotations using the engine directly:

```bash
node --import tsx/esm -e "
import { PolicyEngine } from './src/trusted-process/policy-engine.js';
import { readFileSync } from 'fs';
const policy = JSON.parse(readFileSync('PATH_TO/compiled-policy.json', 'utf-8'));
const annotations = JSON.parse(readFileSync('src/config/generated/tool-annotations.json', 'utf-8'));
const engine = new PolicyEngine(policy, annotations, [], undefined);
const r = engine.evaluate({requestId: 't', serverName: 'git', toolName: 'git_branch',
  arguments: { path: '/some/repo', mode: 'list' }, timestamp: ''});
console.log(r.decision, r.rule);
"
```

The engine inspects the repository a git `path` names (`structural-git-repository-escalate` for a layout or config host git must not run in unseen), so point it at a real repository. The engine alone does not apply the pipeline's argument checks: a call with an argument the annotation does not list is denied by the pipeline (`unannotated-arguments`) before evaluation.

**Multi-mode tool annotations** — Tools with read AND mutation modes (e.g., `git_branch`, `git_stash`, `git_remote`, `git_worktree`, `git_tag`) must have conditional `when` clauses on their path/url arguments so the engine resolves `read-path` only for read operations. Without conditionals, the default roles include all modes (read + write + delete), causing escalate rules to fire even for read-only calls. The discriminator argument name must match the MCP tool's actual input schema: since git-mcp-server 2.15 it is `mode` for all of these tools (`git_branch` names its branches `branchName`/`newBranchName`); a condition on an argument that no longer exists silently falls back to the most restrictive default. All arguments with mutation roles that are absent in read-only modes also need conditional specs (e.g., `git_worktree.newPath`, `git_remote.url`).

**Common validation failures and causes:**

- Read-only operation gets `escalate` → annotation missing conditional `when` clause; mutation roles always active
- Scenario uses wrong argument name (e.g., `operation` instead of `mode`) → conditional roles fall to default (most restrictive). The `filterInvalidSchemaScenarios` validator catches this using the live server's schema when `compile-policy` reaches the server, and the `inputSchema` stored in the annotations otherwise (`--no-mcp`)
- Unconditional allow rule on multi-mode tool → allows mutations too. The compiler prompt forbids this, and the deterministic policy lint (`src/pipeline/policy-lint.ts`) rejects it; allow rules must include `roles: ["read-path"]`

Before committing, always run `npm run format`, `npm run lint` and `npm run typecheck:tests` on new/modified files and fix any issues. The pre-commit hook runs `lint-staged` (Prettier + ESLint) and will reject the commit if there are violations. Common ESLint rules to watch for:

- No non-null assertions (`!`) — use type guards or `as Type | undefined` instead

## Key Conventions

- Workflow staging and bundle copies must not read through links or adopt a changed canonical root. Use `readUntrustedRegularFileBelow(..., { canonicalRoot: true })` for an already-validated root, and `copyRegularFileBelow` with `sourceRoot` for separate canonical copy roots. Revalidate staged roots immediately before reads and mount planning.
- Mux PTY text must pass through `renderCellSpan` in `src/mux/mux-renderer.ts`: preserve its host-width checks and styled-space fallback for uncertain cells. Emitting a PTY span beside an overlay must invalidate the overlay cache so it is repainted afterwards in the same frame.
- ESM modules throughout (`.js` extensions in imports, `"type": "module"` in package.json)
- TypeScript strict mode, target ES2022, Node16 module resolution; Node.js 24 or 26 (`engines` in `package.json`)
- Integration tests spawn real MCP server processes - they need ~30s timeout and create/clean up temp directories in `/tmp/`. Spawn the filesystem server through `test/helpers/filesystem-server.ts` (the exact-pinned package, as shipped), never `npx -y`
- `src/trusted-process/spawn-cwd.ts` owns the working directories of MCP spawns: relays and tool-listing spawns run from the package root (`getTrustedSpawnCwd`), and each relay-spawned backend gets a private per-server directory, never the directory IronCurtain was started in
- The policy engine uses symlink-aware `resolveRealPath()` (from `src/types/argument-roles.ts`) to normalize paths before directory containment checks - both path traversal and symlink-escape attacks are neutralized by resolving to canonical real paths before comparison. On macOS it uses `realpathSync.native`, so policy and transport see the on-disk spelling. When no ancestor resolves it throws `PathResolutionError` (code `PATH_UNRESOLVABLE`), which becomes a `structural-unresolvable-path` deny. Protected paths are matched case- and Unicode-insensitively (`src/trusted-process/protected-paths.ts`)
- Statistics database migrations (`src/llm-metrics/persistence/migrations.ts`) declare `minWriterSchema`/`minReaderSchema`: additive migrations keep the previous values, breaking ones raise them (or use a new table family)
- NEVER add a generated by Claude line to commits or PRs

## Authoring workflow skills

Workflow skills (SKILL.md files under `<workflow-pkg>/skills/` or `~/.ironcurtain/skills/`) carry **domain content**; the FSM and orchestrator carry **control flow**. When adapting prompt material from external sources or refactoring monolithic state prompts:

- Lift substance: bug-class taxonomies, exploitability reference, oracle/disqualifier rules, structured-output schemas, worked examples, technique catalogs.
- Strip ordering scaffolding: stage labels, gate names, "first do X then Y" sequencing, phase numbers. That's FSM territory — skills should not redefine the workflow.
- If material you want to copy is purely about ordering and can't be expressed as an FSM transition, the state graph is wrong before the skill is wrong. Fix the graph; don't smuggle sequencing into a skill.
- A single skill should be loadable by multiple states without contradiction. If a skill assumes "you have already done step N," it's encoding sequencing — split it.

## Module Layering

- `src/pipeline/` is offline tooling. Live-session / hot-path runtime code (`session/`, `sandbox/`, `trusted-process/`, `docker/`, `workflow/`, `memory/`, and other tool-call mediation layers) MUST NOT runtime-import values from `pipeline/`. Offline policy-compilation / customization entry points are an explicit exception — `cron/compile-task-policy.ts`, `persona/compile-persona-policy.ts`, and the `customize-policy` flow legitimately depend on `pipeline/` because they ARE pipeline invocations packaged into consumer modules (`compile-task-policy.ts` is also reached through dynamic imports from `src/index.ts` and `src/workflow/workflow-command.ts`). Type-only contract imports (`import type { ... } from '../pipeline/types.js'`) are also allowed everywhere, since they don't create a runtime edge. If a value-level helper from `pipeline/` is needed on the live runtime path, it's misplaced — relocate it to the consumer's layer (often `trusted-process/`) or a leaf module (e.g., `observability/`). Enforced by the ESLint `no-restricted-imports` rule (direct static imports in the live-runtime directories, `src/web-ui/` and `src/persona/`) and by `test/pipeline-import-boundary.test.ts` (transitive and dynamic imports, from the TypeScript AST).
- Domain modules (`memory/`, `cron/`, `persona/`, `escalation/`) may import from leaves but should not runtime-import session/composition layers. When catching errors across module boundaries, prefer a discriminant string (e.g., `error.code === 'BUDGET_EXHAUSTED'`) over `instanceof` so the catcher doesn't pull in the thrower's module.
- Subclassing a base type from another module (e.g., `cron/HeadlessTransport extends session/BaseTransport`) is NOT a layer violation — base classes are intentional extension points. Composition entry points (`createSession`, `createStandaloneSession`) are similarly callable from any layer that runs sessions. The rule targets _implementation imports_, not _contract imports_.
