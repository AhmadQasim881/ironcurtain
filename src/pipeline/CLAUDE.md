# Policy Compilation Pipeline (`src/pipeline/`)

Two-command offline pipeline. Its artifacts are written under the IronCurtain home (`~/.ironcurtain/generated/` by default, `--output-dir` for others); the reviewed defaults shipped with the package live in `src/config/generated/` (and `generated-readonly/`), and loaders fall back to them.

1. **`npm run annotate-tools -- --server <name>`** (`annotate.ts`) - Developer task. Connects to the specified MCP server, classifies its tool arguments via LLM, and writes the user's **tool-annotations.json overlay** (`~/.ironcurtain/generated/tool-annotations.json`). The overlay holds only servers whose annotations differ from the reviewed package ones; every loader layers it per server over the package file (`src/config/tool-annotations-overlay.ts`, the runtime leaf shared by all loaders; design: `docs/designs/tool-annotation-overlay.md`). When the package was annotated for exactly the live tools (matching `inputHash`), its reviewed annotations are adopted unless the user pinned their own (`--pin`). Tools whose name, description and input schema are unchanged keep their roles (per-tool `annotationKey`), so only new and changed tools go to the LLM; servers that need nothing make no LLM call. Other flags: `--all` (a server that fails to connect, e.g. Docker unavailable for the GitHub server, is skipped with a warning and keeps its annotations; a server whose annotation fails keeps its previous annotations too, and the run exits 1 naming it; the overlay is written after each server), `--diff` (print role changes), `--check [--server <name>]` (compare effective annotations with live tools via `annotation-check.ts`; exit 1 on drift; no LLM), and `--reset [--server <name>]` (remove overlay entries; no LLM or MCP). A legacy full-snapshot user file is rewritten once, keeping `tool-annotations.pre-overlay.json` as a backup. Only needs re-running when servers, tools, or the argument role registry change. Roles are filtered per-server via `serverNames` on `RoleDefinition`. Multi-mode tools (e.g., `git_branch` with list/create/delete modes) get **conditional role specs** — the LLM annotator outputs `{ default, when: [{ condition, roles }] }` blocks instead of static role arrays. See `docs/designs/conditional-argument-roles.md`. To change the shipped annotations, promote reviewed entries with `npx tsx scripts/stamp-package-annotations.ts --from ~/.ironcurtain/generated/tool-annotations.json --server <name>` (run it with no arguments to re-stamp after hand-editing `src/config/generated/tool-annotations.json`); never copy the overlay over the package file, since the overlay omits servers.
2. **`npm run compile-policy`** (`compile.ts`) - User task. Loads annotations, compiles the constitution into **compiled-policy.json**, generates **test-scenarios.json**, and verifies via LLM judge. Flags: `--constitution`, `--output-dir`, `--server <name>` (writes only `servers/<name>/` and leaves the merged policy alone unless `--output-dir` or `--write-merged` is given), `--no-mcp`, `--force`, `--allow-broad-domains`. Exit status: 0 success, 1 failed with no merged policy written, 2 partial failure (the servers listed in `failedServers` have no rules, so their tools are denied). It checks annotation drift against live schemas unless `--no-mcp`.

**Per-server compilation and caching.** Each server is compiled, verified and repaired on its own (`pipeline-runner.ts`). Per-server cache-eligible artifacts are written only after verification passes (`verified: true` in the same atomic write); early, in-repair and failed rules go to `servers/<s>/compiled-policy.unverified.json` and `test-scenarios.unverified.json` for inspection, and a recompile invalidates the old entry first. Verification passes only on the judge's structured verdict plus zero engine failures, never on its prose; a failing server gets up to 3 follow-up verifications (`MAX_FOLLOW_UPS`), each after a repair compile or after scenario corrections. The cache key is `inputHash` (including the LLM prompt text and `POLICY_COMPILER_EPOCH`), plus the `rulesHash` and the `scenarioHash` of the final rules: when only the scenario inputs or the policy-engine semantics changed, the cached rules are re-verified rather than recompiled; a policy-model or verifier-version mismatch only warns; `--force` rebuilds everything, including the cached pre-filter decisions in `servers/<name>/prefilter-decision.json`. Merged policies carry a `provenance` block and `test-scenarios.json` carries `replay` decisions; the shared constants and checks live in the runtime leaf `src/policy-artifacts/` (`provenance.ts`, `canonical-json.ts`, `scenario-replay.ts`), and `scripts/stamp-policy-provenance.ts` stamps the shipped policies. Before merging, `applyOutboundAssessment` (`trusted-process/outbound-rules.ts`) turns allows on outbound-channel tools into `assess`; the compiler model and verifier only ever see allow/escalate. `PipelineRunConfig.skipVerification` (compile only, rules kept as unverified drafts) is used only for `--task-scoped` task policies (`cron/compile-task-policy.ts`, `compileTaskScopePolicy`). An LLM response cut off at its output cap is retried once at `TRUNCATION_RETRY_MAX_TOKENS` (32,768) and otherwise fails as "output truncated" (`OUTPUT_TRUNCATED`, `generate-with-repair.ts`). The pipeline's own `llm-interactions.jsonl` is full detail (not governed by the session LLM-log setting) and created mode 0600.

**Policy lint** (`policy-lint.ts`) - deterministic checks of allow rules against the annotations (`server-wide-allow`, `condition-role-mismatch`, `unconstrained-mutation-allow`, `side-effect-tool-allow` from the servers' `mcpHints`, `broad-path-allow`, `broad-domain-allow`, `duplicate-rule-name`). It runs after each compiler answer (errors are fed back as repair turns), after list resolution, on per-server cache hits (failing rules are recompiled, not served) and on the merged policy before it is written. Broad domains need an explicit opt-in (`--allow-broad-domains`, the constitution directive `<!-- ironcurtain: allow-broad-domains -->`, or a persona's `allowBroadPolicy`).

**Dynamic Lists** - When the constitution references categories ("major news sites", "my contacts"), the compiler emits `@list-name` symbolic references in rules and `listDefinitions` in `compiled-policy.json`. A resolution sub-step (between compilation and scenario generation) resolves each list via LLM (knowledge-based) or LLM+MCP tool-use (data-backed, e.g. contacts). Resolved values are written to **dynamic-lists.json** (`src/pipeline/list-resolver.ts`). At load time, `PolicyEngine` expands `@list-name` → concrete values, with outcome-specific fail-closed matching. Missing, empty, legacy or incompletely validated lists cannot narrow escalation/deny conditions; allow/assess still match only concrete values. Persisted `resolutionState` records completeness; survivor validation and manual additions never repair prior loss. Only a fresh nonempty loss-free resolution becomes complete. Three list types: `domains` (wildcard matching via `domainMatchesAllowlist`), `emails` (case-insensitive), `identifiers` (exact match), defined in `dynamic-list-types.ts`. Domain values are checked with the Public Suffix List (no IPs, local names, single labels, unknown TLDs, public suffixes or broad wildcards), `*.value` is added only where `canAutoWildcard` allows it, cached and merged lists are re-checked, and compile-policy and refresh-lists print the values they added and removed. Domain-typed lists go in `DomainCondition.allowed`; non-domain types use `ListCondition` (new field on `CompiledRuleCondition`); the compiler's catch-all check treats an empty `lists` as no condition.

- **Data-backed resolution is policy-mediated** (`proxy-mcp-connections.ts`): every resolver tool call goes through a `ToolCallCoordinator` with the bundled read-only policy, escalations denied, no `allowedDirectory`, and an audit log (`list-resolution-audit.jsonl` next to the artifacts). A data-backed list must name its server (`mcpServerHint`); only that server is connected (one relay with `SERVER_FILTER`), and network-egress servers such as fetch can never back a list (`getMcpListScopeError`). `list-resolution-tools.ts` decides which tools the resolver LLM is told about.
- **Overrides and naming** (`list-merge.ts`): users edit `manualAdditions`/`manualRemovals` in the policy's merged `dynamic-lists.json`; they survive compile-policy and refresh-lists. Per-server `servers/<server>/dynamic-lists.json` copies hold resolver output only. A list name that servers define differently becomes `<server>--<name>` (`sourceName` records the original). `ironcurtain refresh-lists` re-resolves without full recompilation and writes through to the per-server copies. For the package's own policy, which refresh-lists cannot write next to, it writes `~/.ironcurtain/generated/dynamic-lists.json`, which loaders layer over the shipped lists (`layerUserDynamicLists` in `src/config/index.ts`): the user's overrides always apply, and the user's values replace the shipped ones only when they come from the same definition and are no older (a newer shipped resolution wins). An entry with an empty `inputHash` is an unresolved `--no-mcp` placeholder. Legacy/incomplete entries are refreshed rather than used as resolver cache hits; scenario hashes cover served revalidated values, completeness and overrides. Sessions, refresh-lists and compile-policy refuse a malformed `dynamic-lists.json` with field-level errors (strict reader: `src/config/dynamic-lists-file.ts`).

## Runtime invariant

This directory is offline tooling, used by commands such as `annotate-tools`, `compile-policy`, `refresh-lists`, and `customize-policy`, plus other policy-compilation/customization flows packaged into consumer modules (e.g., `cron/compile-task-policy.ts`, `persona/persona-customizer.ts`). Live-session runtime code (anything on the tool-call mediation hot path — `session/`, `sandbox/`, `trusted-process/`, `docker/`, `workflow/`, `memory/`) MUST NOT import runtime values, helpers, or implementations from here. Type-only / contract imports from `pipeline/types.ts` are allowed and expected (the compiled-policy and annotation file shapes are defined there); broadly-shared contracts may eventually move to a leaf module, but until then `import type { ... } from '../pipeline/types.js'` does not constitute a runtime dependency. If a value-level helper turns out to be needed on the live runtime path, that signals it is misplaced: move it to the consumer's layer and leave only compile-time concerns here. Past extractions: `getListMatcher` → `trusted-process/list-matcher.ts`; `createLlmLoggingMiddleware` → `observability/llm-logger.ts`.

The rule is enforced twice: the ESLint `no-restricted-imports` rule (`eslint.config.js`) bans direct static value imports from `src/pipeline` in `src/{session,sandbox,trusted-process,docker,workflow,memory}/**`, `src/web-ui/**` and `src/persona/**` (except the two sanctioned persona modules, `compile-persona-policy.ts` and `persona-customizer.ts`), and `test/pipeline-import-boundary.test.ts` parses the import graph with the TypeScript AST to forbid transitive static reach and dynamic pipeline imports from the live-runtime directories (seams included, except a CLI entry point's dynamic import of its own seam, `CLI_ENTRY_SEAM_IMPORTS`: `workflow/workflow-command.ts` -> `cron/compile-task-policy.ts`; every pipeline module except `types.ts` counts). In `src/web-ui/` and `src/persona/` it forbids static value paths and direct dynamic imports of pipeline modules, so they reach the pipeline only through a seam.

Constitution review displays must render the full original/proposed policy with `toDisplayText`, without trimming leading format characters or shortening permission lines. Escape diff lines before adding trusted styling; quote model-derived questions, summaries, progress and errors in both parallel and sequential progress reporters. Stored policy bytes remain unchanged (RV-20).
