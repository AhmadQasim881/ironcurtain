# Trusted Process (`src/trusted-process/`)

## Overview

The security kernel of IronCurtain. Every tool call from the agent passes through this layer for policy evaluation, audit logging, and routing to real MCP servers.

**`ToolCallCoordinator`** (`tool-call-coordinator.ts`) — centralizes all security-kernel components as single instances: PolicyEngine, AuditLog, CallCircuitBreaker, ApprovalWhitelist, AutoApprover, and ServerContextMap. Instantiated once per session in the Sandbox/CodeModeProxy layer. Two mutexes serialize concurrent access: a call mutex (protects RMW caches during `handleToolCall`; an escalation wait releases it) and a policy mutex (taken by `loadPolicy` to swap the active `PolicyEngine` between workflow states). A `currentPersona` field tracks the persona that installed the active policy; the security pipeline stamps it onto every `AuditEntry`. Further responsibilities, each described in the file header:

- `handleToolCall` / `handleStructuredToolCall` take host-assigned `ToolCallOptions`: `signal` (the Code Mode chain aborts it when its script ends; a pending escalation is then withdrawn, a late approval is not acted on and audited as `call-cancelled`, and a backend call in flight is cancelled) and `lane` (the circuit-breaker lane, one per agent connection to the Code Mode proxy).
- `close()` and `loadPolicy()` cancel pending escalations (audited `cancelled`, never as a human denial) instead of waiting out the escalation timeout.
- Audit failures fail closed: once the pipeline reports `AUDIT_LOG_UNAVAILABLE`, the coordinator latches it (`getAuditFailure()`) and refuses every later call at admission.
- Live-schema drift: when a server registers its tools the coordinator compares them with the stored annotations (`schema-drift.ts`) and keeps the result (`getSchemaDrift()`); sessions turn it into an `annotation_drift` diagnostic. It writes nothing to stderr.
- Optional state fixed at construction and kept across `loadPolicy`: the `--task-scoped` task scope, the read-only workspace, the monotonic taint state (opt-in, replayed from the audit log at construction), and the `workflowCommit` handler that registers the virtual `workflow` server's `workflow_commit` tool.
- `authorizeEgress()` decides opt-in MITM egress (`egress-policy.ts`). It is admitted like a tool call but never takes the call mutex.

**`tool-call-pipeline.ts`** — the security pipeline. Contains `handleCallTool` and all helpers: argument validation (calls carrying an argument the stored annotation does not list are denied, rule `unannotated-arguments`; proxy tool arguments are validated before policy evaluation by `validateProxyToolArguments`), `prepareToolArgs` normalization, git enrichment, policy evaluation, the opt-in outbound content assessment and taint escalation, the escalation flow, auto-approval, whitelist matching, roots expansion, circuit breaker check, dispatch (`workflow_commit` is dispatched in-process to the coordinator's handler), audit writes (a write-ahead `dispatching` record before the first side effect, then the outcome record), and the `ServerContext` post-success update. Human approvals (never auto-approvals or whitelist matches) are reported through `CallToolDeps.onHumanApproval`; the coordinator appends them to `~/.ironcurtain/approval-history.jsonl` under the scope in effect (`approvalHistoryScope`, moved per persona by `loadPolicy`).

**`mcp-proxy-server.ts`** — pure MCP relay subprocess. Spawned per backend server by `MCPClientManager`, and by the pipeline's list resolver (`connectViaProxy`, one relay per named server with `SERVER_FILTER`). Handles OAuth credential injection, sandbox-runtime wrapping, and stdio MCP transport. Forwards `CallTool` requests to the real backend and returns raw results (`structuredContent` included). No policy evaluation, no audit writes, no escalation handling. Every backend, sandboxed or not, runs in a private per-server working directory (`spawn-cwd.ts`) with an allowlisted environment (`buildBackendEnv` over `child-env.ts`; the `git` backend additionally gets the hardened git environment from `git-backend-env.ts`). The relay exits when `ALLOWED_DIRECTORY` or `IRONCURTAIN_HOME` is set to a relative path. Bridges roots: when the coordinator sends `notifications/roots/list_changed`, the relay fetches the new list via `server.listRoots()`, updates the shared `relayRoots` array, and forwards the notification to each backend client so they re-query; a backend confined to its roots (`sandbox.filesystem.confineToRoots`, the filesystem server) is instead restarted under a new srt profile (`roots-confinement.ts`). Docker-based backends (e.g. github's `docker run -i --rm ...`) are translated to the Apple `container` CLI by `container-command.ts` when `docker` is absent but `container` is present; backends that fail to connect (missing binary, runtime down, startup crash) are warn-skipped per server, with the `proxyCanServe` guard exiting the relay non-zero only when zero backends connect.

**`TrustedProcess`** (`index.ts`) — thin wrapper around `ToolCallCoordinator` that spawns backends directly through its own `MCPClientManager` (no relay subprocess, no srt wrapping, so it never stamps `sandboxed: true`). Used only by tests (`test/integration.test.ts`, `test/trusted-spawn-cwd.test.ts`); `TrustedProcessOptions.onEscalation` is the in-process escalation callback they use.

**`ControlServer`** (`control-server.ts`) — small HTTP server bound to a Unix domain socket (or loopback TCP) that exposes `POST /__ironcurtain/policy/load`. The workflow orchestrator hits this endpoint between agent states to hot-swap the coordinator's active `PolicyEngine` and `currentPersona` via `ToolCallCoordinator.loadPolicy({persona, policyDir})`. The control server only runs in workflow shared-container mode; `DockerProxy.getPolicySwapTarget()` is the narrow seam that exposes `startControlServer(opts)` without leaking the rest of the coordinator. Single-session CLI / daemon / cron paths never construct it. See [`docs/designs/workflow-container-lifecycle.md`](../../docs/designs/workflow-container-lifecycle.md).

**Deterministic commands are not mediated.** Workflow deterministic states with
`container: true` are run by the host orchestrator via `docker exec` into the
workflow's shared container. This is intentionally not a `ToolCallCoordinator`
tool call: the command argv comes from trusted workflow YAML, not from the
agent. The boundary is the workflow container (`/workspace` read-write,
`/workflow-scripts` read-only, no runtime network), and the result is reduced
to the deterministic state result contract by the orchestrator. The agent has
sudo in that container, writes `/workspace` and owns the run's read-write
dependency layers (per run, never shared across runs), so a helper's verdict
is only as trustworthy as that run. States with `host: true` run their argv on
the host as the user, outside both the container and the policy engine
(`src/workflow/host-command-runner.ts`), which is why validation demands that
explicit per-state acknowledgement.

## Policy Engine

**PolicyEngine** (`policy-engine.ts`) - two-phase evaluation with default-deny (the file header is the authoritative description):

- **Structural invariants** (hardcoded, never overridden by compiled rules): protected paths (`structural-protected-path`, matched spelling-insensitively and still protected inside the sandbox, see `protected-paths.ts`), paths that cannot be resolved (`structural-unresolvable-path`), unknown tools (`structural-unknown-tool`), local or cloud-metadata destinations (`structural-local-destination-deny`), changes to a read-only workspace (`structural-read-only-workspace`, checked before sandbox containment), and per-role sandbox containment (`structural-sandbox-allow`). Four structural escalations are recorded rather than returned, so compiled rules still run and a compiled deny wins over them: the domain gate for URL roles (`structural-domain-escalate`; a server without `sandbox.network.allowedDomains` gets the default `['*']`, which passes names and escalates IP literals), a write or delete inside a `.git` directory (`structural-git-internals-escalate`), a git repository whose layout or config host git must not run in unseen (`structural-git-repository-escalate`: redirects, worktree, include, driver, configured hook, alternates or unreadable config; see `git-structural-rules.ts`), and a role-bearing argument holding a nested object or array (`structural-nested-argument-escalate`, human-only; its strings and numbers are still checked by the deny-side and compiled rules). The two git escalations are approved per call and never whitelisted (`requiresPerCallApproval`). A git remote argument that names a local repository is evaluated as a read of that path (so a remote resolving to a protected path is denied).
- **Compiled rules**: declarative rules from `compiled-policy.json`. Each role is evaluated independently (first match per role); the most restrictive result across roles wins: deny > escalate > assess > allow, where `assess` is an allow subject to the opt-in outbound content assessment. A rule whose outcome is none of these denies; the loaders already reject such files (`src/types/policy-schema.ts`). When a policy is loaded, `outbound-rules.ts` turns every allow that can match an outbound-channel tool into `assess`.
- **Task scope** (optional, `--task-scoped`, loaded by `task-scope.ts`): a second compiled policy intersected with the session policy. A call is allowed only when both allow it; a role no task rule covers escalates (`task-scope-escalate`).

An escalation names every role that escalated (`escalatedRoles`), so a whitelist pattern must cover all of them; `humanOnly` marks escalations that only a human, one call at a time, may decide (never the auto-approver, a whitelist pattern or "approve all"). Path resolution: `allowedDirectory` and every rule's `paths.within` are canonicalized once per engine (a hot-swap builds a new engine); call paths and protected original names/current targets/full controlling link chains are checked per evaluation. Workspace admission also rejects ownership of traversed components, including those later canceled by `..`. Delete-role operands cannot contain a protected descendant. A workspace-derived rule root resolving outside the workspace fails closed on load/reload, including an external name whose link chain enters the workspace; explicitly trusted external roots remain supported.

The coordinator and MCP relay use `argument-budget.ts` to check every tool argument tree before backend dispatch. The 4,096-node limit includes the root at depth zero, and the maximum depth is 32. For a call over the whole-tree limit, the coordinator records its request identity, fixed reason and empty arguments. Admission before path normalization and direct engine evaluation also limits role-bearing scalar values to 256 per argument and 1,024 per call, with 16 KiB per resource value and 256 KiB of resource characters. The in-process Code Mode JSON bridge caps serialized UTF-8 arguments at 1 MiB. `git_wrapup_instructions` requires a tracked absolute working directory from trusted coordinator state, then human per-call approval; missing context denies with a `git_set_working_dir` instruction. Every selected Git repository is refused when it contains a specific current protected descendant, even for metadata-only calls; selectors are never rewritten. A protected cwd audit/config file must be relocated outside the repository to enable its Git tools. Submodule metadata/named configuration also requires per-call structural review; shared git defaults disable implicit recursion without claiming child internals were inspected.

The annotation map stores `StoredToolAnnotation` (may contain conditional role specs for multi-mode tools). `resolveStoredAnnotation()` resolves conditionals against call arguments, producing a plain `ToolAnnotation`. `getAnnotation(server, tool, callArgs)` returns the resolved annotation; `getStoredAnnotation()` provides raw access for pipeline tools.

**Supporting modules:**

- `policy-types.ts` - `EvaluationResult` type with `escalatedRoles` for whitelist candidate extraction and `humanOnly`.
- `policy-roots.ts` - `extractPolicyRoots()` derives MCP Roots from `allow`/`escalate` rules with `paths.within` conditions. `extractRequiredServers()` derives the set of MCP server names referenced by the compiled policy; the standalone session path and the workflow infrastructure factory both use it to skip spawning proxy subprocesses for unreferenced servers (default-deny would reject every call to them anyway). `rootUriForPath`/`pathForRootUri` convert with `pathToFileURL`; `directoryForPath` resolves relative paths against the sandbox.
- `domain-utils.ts` - domain matching (`domainMatchesAllowlist`, `isIpAddress`, `isLocalOrMetadataHost`), URL normalization, and `resolveUrlForDomainCheck`, the single URL-role resolver that the engine, the approval whitelist and the escalation prompt must share. Also `parseGitRemoteUrl` (git-faithful host parsing), `displayableDomain`, `describeGitRemoteDestination` and `isPlainGitRemoteName`. An omitted git remote is evaluated as `origin`.
- `git-remote-resolution.ts` - in-process resolution of named remotes and URL rewrites (`pushurl`, `insteadOf`, `pushInsteadOf`) from the repository's `.git/config` (read only inside the sandbox, no-follow and size-capped) and the user's system/global config. It never runs git in an agent-writable repository; layouts it cannot emulate are refused.
- `git-structural-rules.ts` - the `.git` write/delete escalation, static inspection of a repository before host git runs in it, and local git sources as filesystem reads.
- `protected-paths.ts` - `isProtectedPath` (with the per-entry sandbox exemption) and `foldPathForComparison`, used for deny-side matching only.
- `path-utils.ts` - annotation-driven path normalization via `prepareToolArgs()`. Resource-role arguments give transport and policy identical values: relative paths are resolved against `allowedDirectory` and canonicalized, so the MCP server never resolves them against its own working directory.
- `argument-values.ts` - `argumentValues`, `isStructuredValue`, `ownArgument`: the values policy reads from an argument; a non-flat value is reported as structured.
- `list-matcher.ts` - runtime matching for dynamic list types (`ListCondition`).
- `trusted-server-policy.ts` - per-tool policy for trusted servers (today only the memory server): reads and single-fact writes are allowed, bulk forgets and large ingests escalate human-only, unknown tools are denied.
- `taint-policy.ts` - opt-in sequence-aware policy (`taintEscalation.enabled`): `TaintClassifier`, `SessionTaint`, `evaluateWithTaint`, `restoreTaintFromAuditLog`. After a taint source, sink calls that policy does not deny escalate human-only (`taint-escalation`). The audit records taint facts (`AuditEntry.taint`).
- `assessment.ts`, `assessment-detectors.ts`, `assessment-config.ts` - opt-in outbound content assessment (`contentAssessment`): deterministic detectors plus an optional LLM check. Verdicts map to allow or escalate, never to deny or to allow on error; content-assessment escalations are human-only. The audit records the verdict (`contentAssessment` field).
- `egress-policy.ts` - opt-in MITM egress policy (`egressPolicy.enabled`): the virtual `network` server (`network/request`, `egress-host` role), its allowed-hosts and human-only escalate rules, and `decideEgress`. `network` and `workflow` are reserved server names.
- `schema-drift.ts` - compares stored annotations with live schemas (also used offline by `doctor`, `annotate-tools --check` and `compile-policy`).
- `workflow-commit-tool.ts` - the coordinator-owned `workflow_commit` virtual tool and its hardcoded annotation and allow rule, merged at construction and on every `loadPolicy`.

## Approval & Escalation

**ApprovalWhitelist** (`approval-whitelist.ts`) - session-scoped in-memory store of approval patterns extracted from user-approved escalations. Only converts `escalate` to `allow`, never overrides `deny`, never matches a human-only escalation. Entries are never persisted to disk. Constraints are typed by kind: `path`, `directory`, `domain`, or `exact`. A pattern discharges a later escalation only when it constrains every role in that call's `escalatedRoles`. Candidates come narrowest first (exact paths, which `/approve+` selects, then a directory-wide one that is not offered for the root, the home directory or credential and startup directories); a candidate is offered only when it discharges the call it came from. URL constraints bind the destination resolved by `resolveUrlForDomainCheck`, again at every match, so a named git remote is bound to where it connects.

**AutoApprover** (`auto-approver.ts`) - optional LLM-based intent matcher that auto-approves escalations when the user's message clearly authorizes the action. Uses a cheap model (default: Haiku 4.5), configurable via `autoApprove` in user config. Can only return `approve` or `escalate` (never deny). Off by default. Never consulted for human-only escalations. Everything derived from the agent's call is passed as one JSON-encoded data block, and a deterministic anchor check first requires every escalated value to appear in the human's message. PTY sessions trust only context written by their trusted front-end (`isPtySession` in `ToolCallCoordinatorOptions`).

**Escalation waits** - bounded by `escalationTimeoutSeconds` (30-600 s, `call-timeouts.ts`, which also bounds backend calls and Code Mode chains). A wait ends without a decision when it times out, is cancelled (`close()`, `loadPolicy`, or the caller's signal) or is withdrawn by an in-process handler (`EscalationWithdrawnError`, `escalation-wait.ts`). The in-process `EscalationPromptFn` receives `details` (escalation id, persona, abort signal).

**Human approval front-ends.** File-IPC escalations reach the session's transport: the CLI (`CliTransport`) offers `/approve [N]`, `/approve+ [N]` (whitelist the exact pattern), `/approve+dir [N]` (the directory-wide pattern, when offered) and `/deny [N]`; the mux, web UI and Signal have their own. `escalation-context.ts` builds the reviewer context (the human's last trusted message, the task summary, and the agent's own bounded, labelled justification from `setAgentJustificationProvider`, which never reaches the auto-approver).

**Roots expansion** (`roots-expansion.ts`) - after an approval, adds MCP roots for the escalated paths only, taken from the canonical paths evaluated before the wait and re-checked after it (deny `approved-path-changed`), never at or under the sandbox or the IronCurtain home. It reads the backend's allowed directories back and closes the connection on a mismatch (deny `roots-verification-failed`; later calls to that server get `no-client-connection`). For confined servers the coordinator refuses roots that cannot be exposed (`root-not-exposable`).

**ServerContext** (`server-context.ts`) - tracks per-server state from successful tool calls to enrich escalation requests for human reviewers. The git working directory is set by `git_set_working_dir` and cleared by `git_clear_working_dir`; `git_clone` does not touch it. The pipeline uses it for git calls that leave the repository path to the server's working directory.

**Atomic file writes:** All file writes in the escalation IPC protocol use `atomicWriteJsonSync()` from `src/escalation/escalation-watcher.ts` (write to `.tmp`, then rename).

## MCP Client & Transport

**MCPClientManager** (`mcp-client-manager.ts`) - manages stdio-based MCP client connections and spawns relays from IronCurtain's package root (`getTrustedSpawnCwd`). Unavailable servers are logged as warnings and skipped gracefully. The sandbox connects relays concurrently (`RELAY_CONNECT_CONCURRENCY` in `src/sandbox/index.ts`) and reports skipped ones (`Sandbox.getUnavailableServers`).

**Spawn hygiene:** `spawn-cwd.ts` owns the working directories of every MCP spawn (the package root for relays and tool-listing spawns, a private `<server>.cwd` per relay-spawned backend); `child-env.ts` owns the allowlisted environments; `git-backend-env.ts` fixes the hardened git environment (from `src/security/git-hardening.ts`) for the `git` backend.

Developer tool discovery (`scripts/mcp-discovery.ts`) uses `pipeline/live-tools.ts`'s `discoverLiveTools`, including the effective sandbox policy, stored server credentials and credential-protection paths. It closes the discovery run in `finally`; it does not construct a separate stdio launcher or inherit the complete host environment. The caller's client name labels diagnostics only.

**Relay diagnostics:** `relay-diagnostics.ts` makes stderr text inert and single-line before `emitProxyDiagnostic` writes it synchronously; pipeline relay forwarding applies the same display boundary. Startup stderr capture retains a bounded complete sample for credential redaction, then the error preview is shortened. If capture exceeds its limit, the sample is omitted as a whole so a credential cut at the boundary cannot leak a prefix. Persistent session logs keep their existing redaction path.

**CallCircuitBreaker** (`call-circuit-breaker.ts`) - centralized rate limiter managed by the ToolCallCoordinator. Denies repeated identical (tool, argsHash) calls exceeding a sliding-window threshold (default: 20 calls per 60s). Windows are kept per lane, plus an all-lanes window bounding the total at the threshold times the coordinator's `maxLanes` (1 outside fan-out workflow bundles). Runs after policy evaluation so every call is audited.

**Transport layers** for Docker Agent Mode:

- `socket-connection-transport.ts` - one accepted socket bridged to an MCP `Transport` with its own read buffer: a malformed frame is reported through `onerror` and the connection continues, a frame over 10 MiB destroys only that socket, and `onmessage` exceptions never escape.
- `uds-server-transport.ts` - Unix domain socket transport (Linux containers with bind mounts).
- `tcp-server-transport.ts` - TCP transport (macOS Docker Desktop where VirtioFS does not support UDS in bind mounts).

Both listeners wrap every accepted connection in a `SocketConnectionTransport` and cap simultaneous connections (default 64). Multi-client mode (`onconnection`, used by `CodeModeProxy`) gives each connection its own MCP `Server`; single-client mode refuses, rather than evicts, a second client (used only by `mcp-proxy-server`'s `PROXY_SOCKET_PATH`/`PROXY_TCP_PORT` modes).

The legacy relay `PROXY_TCP_PORT` mode binds only `127.0.0.1` and requires `IRONCURTAIN_MCP_TCP_TOKEN` as 64 lowercase hexadecimal characters. Missing or malformed credentials stop the relay before backend setup. Clients must send the bounded `IRONCURTAIN_AUTH/1 <token>\n` preface before MCP or health traffic. The token is relay-internal and cannot be inherited or forwarded through backend `-e NAME` passthroughs. Existing tokenless or LAN clients must migrate; supported session relays use stdio. Docker Desktop CodeMode TCP additionally encrypts the sidecar-to-host hop with verified TLS; UDS and stdio behavior are unchanged.

**PermissiveOutputValidator** (`permissive-output-validator.ts`) - bypasses MCP SDK client-side `structuredContent` schema validation. IronCurtain proxies responses as-is, so strict validation would hide real error messages from servers that return non-conforming error content.

**MCP error handling** (`mcp-error-utils.ts`) - `extractMcpErrorMessage()` digs into schema validation error `data` to surface the original server error. `error-prefixes.ts` holds the prefixes that tag error responses by category.

## Audit

**AuditLog** (`audit-log.ts`) - append-only JSONL logging (synchronous appends) with PII/credential redaction enabled by default (`audit-redactor.ts`). Redaction masks credit cards (Luhn-validated), dash-separated SSNs, well-known provider and service key formats (Anthropic, OpenAI, OpenRouter, GitHub, Google, Slack, AWS), JWTs and bearer tokens, plus the exact credential values IronCurtain holds (`audit-secrets.ts`, a snapshot taken when the coordinator is built). Disable with `auditRedaction.enabled: false`. Every allowed call that acts gets a write-ahead `dispatching` record (same `requestId`) before its first side effect, then its outcome record; readers that want one record per call filter with `isDispatchingAuditEntry` (`src/types/audit.ts`). The pipeline calls `assertWritable()` before evaluating a call, and every failure carries the code `AUDIT_LOG_UNAVAILABLE`: a write error latches and refuses all later calls. The audit file is fixed at coordinator construction; workflows produce a single `audit.jsonl` per run and `loadPolicy` does not rotate it — each `AuditEntry` carries a `persona` field instead, so per-persona slices are reconstructed by scanning.

CLI JSON display is a separate sink boundary: `audit report|proposals|verify --json`, prune reports, statistics summaries, nested-workload status and workflow watch escape terminal-active and default-ignorable characters with `toTerminalSafeJsonText`. Parsing stdout yields the original values; workflow watch also flattens valid CR/tab whitespace outside JSON strings. These display changes do not rewrite persisted evidence or argument-validation results. Amendment derivation withholds control/default-ignorable values that cannot be quoted safely in a policy statement.

## Sandbox & Credentials

**Sandbox Integration** (`sandbox-integration.ts`) - wraps sandboxed MCP servers in `srt` (sandbox-runtime CLI) processes for OS-level containment. Each sandboxed server gets its own `srt` process with per-server network isolation. Config: `"sandbox": false` to opt out, omit for restrictive defaults, or specify `{ filesystem, network }` overrides. Every sandboxed server's `denyRead` is unioned with a read-containment baseline: the IronCurtain home, the per-user credential stores and the relays' private scratch root. Path-only additions carry configured `credentialProtection.extraPaths`, trusted environment-file paths and every effective/default/XDG Anthropic CLI credential candidate through session, discovery, resolver and doctor relay launches. `sandbox-credential-paths.ts` validates bounded relay-only metadata; it is never forwarded to a backend. The git backend's macOS socket profile names exactly the canonical `SSH_AUTH_SOCK`, not its parent directory. A server opts out of one credential-store entry only by naming it exactly in its own `allowRead`; an `allowRead`/`allowWrite` entry inside the IronCurtain home (other than the session sandbox) is refused with `SandboxConfigError` (`reexposesIronCurtainHome()`). `confineToRoots` servers also have the home, temporary and runtime directories hidden (`confinementHiddenRegions`); `roots-confinement.ts` re-exposes their roots and program and restarts them when their roots change.

**OS sandbox policy:** `sandboxPolicy: "enforce" | "warn"` (`src/config/sandbox-policy.ts`; default `"enforce"` on Linux and macOS) decides what happens to a server that asks for an OS sandbox when sandbox-runtime cannot provide one (unsupported platform, or bubblewrap, socat or ripgrep missing): under `enforce` that server does not start and the others keep running; under `warn` it runs unconfined with a session warning. `planServerSandboxing` decides per server and drives spawning, refusal, the audit stamp and the notice. The audit's `sandboxed` field is `true` inside an OS sandbox, `false` when a requested sandbox was unavailable, and absent for opted-out servers.

**Google Workspace credentials** (`gworkspace-credentials.ts`) - writes OAuth credential files for `@alanse/mcp-server-google-workspace`. Intentionally omits `refresh_token` to prevent token rotation races; IronCurtain's OAuthTokenProvider is the sole token authority.

**TokenFileRefresher** (`token-file-refresher.ts`) - proactive OAuth credential file refresher running in the proxy process. Periodically checks token expiry and writes fresh files before access tokens expire (default: check every 5 min, refresh at 10 min before expiry).

## Tool Description Hints

**ToolDescriptionHints** (`tool-description-hints.ts`) - loads hints from `src/config/tool-description-hints.json` and appends them to proxied tool descriptions. Helps agents use MCP tool parameters correctly (e.g., avoiding CLI flags in structured parameters).
