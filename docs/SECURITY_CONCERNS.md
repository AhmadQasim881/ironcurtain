# Security Concerns and Threat Landscape

**Status:** Living document.

**Last verified against code:** 2026-11-14, at commit `1471366e`.

This document lists the known security concerns, attack vectors and residual risks of the IronCurtain runtime: where the "dragons" live. It is written for security researchers, auditors and developers. [SANDBOXING.md](../SANDBOXING.md) describes the defense layers; this document describes what they stop and what they do not.

How to read it:

- Every mitigation names the module that implements it. Anything that is not implemented says so (**planned**, **not implemented**).
- **Opt-in** marks a control that is off by default.
- **Residual risk** lists what remains open.
- A change under `src/docker/` or `src/trusted-process/` must be checked against this document; the pull request template has a checklist item for it. Whoever re-checks the whole document against the code updates the "Last verified against code" line.

## 0. Threat Model and Trust Boundaries

**Untrusted:** the agent, meaning the LLM and everything it runs (Code Mode scripts in the V8 isolate, every process in a Docker agent container); everything it reads (web pages, email, repository files, MCP tool results); memory written by earlier sessions; and artifacts written by other agents of a workflow. A compromised agent is the expected case, not an edge case.

**Trusted:** the user, the host IronCurtain process (the security kernel in `src/trusted-process/`, the MITM proxy in `src/docker/mitm-proxy.ts`, the MCP relays in `src/trusted-process/mcp-proxy-server.ts`), the host OS and kernel, the container runtime, and the user's account. A compromised host or user account is out of scope: IronCurtain cannot protect against root or admin access.

**Local isolation is partial.** IronCurtain keeps its own state owner-only: the daemon control socket (`src/daemon/control-socket.ts`), the relays' scratch root (`src/trusted-process/spawn-cwd.ts`), the MITM certificate authority (`src/docker/ca.ts`). Known exceptions are listed as residual risks (for example the loopback TCP endpoints of macOS Docker Desktop sessions, §9), and the OAuth authorization URL, with its state and code challenge, is visible on the browser launcher's command line during third-party OAuth setup (`src/auth/oauth-flow.ts`).

| Boundary              | What it decides                                           | Implementing modules                                                                               |
| --------------------- | --------------------------------------------------------- | -------------------------------------------------------------------------------------------------- |
| Policy engine         | Every MCP tool call: allow, deny or escalate              | `src/trusted-process/policy-engine.ts`, `src/trusted-process/tool-call-pipeline.ts`                |
| MITM proxy            | Every network request a Docker agent container makes      | `src/docker/mitm-proxy.ts`, `src/docker/registry-proxy.ts`                                         |
| V8 isolate, container | What agent code can touch directly                        | `src/sandbox/code-mode-chain.ts`, `src/docker/agent-privileges.ts`, `src/docker/docker-manager.ts` |
| OS sandbox            | What an MCP server process can read, write and reach      | `src/trusted-process/sandbox-integration.ts`                                                       |
| Human escalation      | Escalated tool calls and escalated egress destinations    | `src/trusted-process/tool-call-pipeline.ts`, `src/escalation/`, `src/mux/`, `packages/web-ui/`     |
| Audit log             | Records every decision; refuses to dispatch when it can't | `src/trusted-process/audit-log.ts`                                                                 |

**Not enforced** (each is detailed below):

- Inside a Docker agent container the agent acts on its read-write bind mounts (workspace, conversation state, workflow dependency layers) directly. The policy engine sees only MCP tool calls and the MITM proxy sees only network traffic (§2b).
- Traffic through an approved passthrough domain is not inspected (§2b-i).
- In Docker Agent Mode, budgets cover tokens and cost at the MITM proxy and wall-clock time per turn; steps are counted per turn, not per tool call (§9).
- Prompt-level mitigations (memory framing, compaction summary framing) do not bind a model that chooses to follow injected text (§4, §13).

## 1. The Policy Compilation Gap

**Risk:** The bridge between human intent (the constitution) and machine enforcement (the policy engine) is an LLM-based compilation pipeline (`ironcurtain compile-policy`, `src/pipeline/`).
**Impact:** Critical. If the compiler hallucinates, misreads a negative constraint ("do not allow X" becomes "allow X"), or misses a tool argument, the runtime enforces a flawed policy.
**Mitigation:**

- **Default-deny:** a call that matches no rule is denied (`src/trusted-process/policy-engine.ts`).
- **Hardcoded structural invariants** (`evaluateStructuralInvariants` in `src/trusted-process/policy-engine.ts`), never LLM-generated and not overridable by compiled rules, in this order: protected paths (deny, matched case- and Unicode-insensitively, `src/trusted-process/protected-paths.ts`); fetch URLs that name a local or cloud-metadata host (deny, `isLocalOrMetadataHost` in `src/trusted-process/domain-utils.ts`); changes outside the writable directories of a read-only workspace (deny); sandbox containment (allow); structural escalations (the untrusted-domain gate, writes inside `.git`, git repositories whose configuration host git must not act on unseen (`src/trusted-process/git-structural-rules.ts`), and role-bearing arguments that hold nested objects or arrays, which are human-only); unknown tools (deny). A path that cannot be resolved is denied (`structural-unresolvable-path`).
- **Protected path names and parents:** original names, current canonical targets and controlling links are checked on each call. Workspace admission rejects control of traversed components, including those canceled by `..`. Delete-role operands cannot contain a protected descendant; reading/listing an ordinary parent remains policy-controlled. Workspace-derived rule roots that resolve outside the workspace fail closed on reload.
- **Protected paths stay protected:** a protected path inside the session sandbox or a `--workspace` stays denied for every MCP-mediated access, in either session mode. A protected entry that is, or lies below, a symbolic link whose target is missing (a dangling dotfile link, a link onto an unmounted volume) also protects that target and every other link on the way to it, so an agent can neither create the file a later host run would read through it nor replace a link that leads there (`resolveDanglingLink` in `src/types/argument-roles.ts`, deny side only). The protected set includes the trusted credential files (`$IRONCURTAIN_HOME/.env` and an explicit `--env-file`, `src/config/trusted-env.ts`; a `.env` in the working directory is never read) and the host credential stores (`src/config/credential-stores.ts`: the Claude, Anthropic CLI and Codex credential files and `<home>/oauth` always, and by default SSH, AWS, GnuPG, gcloud, Docker, git-credentials, netrc, npmrc, gh and kube configuration).
- **Workspaces cannot contain trusted state:** a workspace may not be or contain the home directory, the IronCurtain home, the package configuration, the relays' private scratch root (`<os.tmpdir()>/ironcurtain-<uid>`, so on Linux `/tmp` is refused) or any protected path (a dangling protected link counts at its target too, and no workspace may hold another link on its way there), and may not lie inside the IronCurtain home (apart from IronCurtain's own managed workspaces), the package configuration, the scratch root or a protected path; containment is decided by file identity, not spelling (`src/session/workspace-validation.ts`). The one protected path a workspace may contain is the audit log named by a relative `AUDIT_LOG_PATH` (by default `./audit.jsonl`), which sessions never use, so that `-w .` works. This is the boundary in Docker Agent Mode, where the workspace is bind-mounted read-write and its files never pass through the policy engine.
- **Arguments must be annotated:** an argument the stored annotation does not classify is denied before evaluation (`unannotated-arguments` in `src/trusted-process/tool-call-pipeline.ts`), whatever the server's live schema accepts. Annotation fixes that ship with IronCurtain reach users who annotated their own servers, because user annotations are a per-server overlay (`src/config/tool-annotations-overlay.ts`). Both annotation files are read like the compiled policy: a symlink at the file's name (even a dangling one) or a file another local user can write is refused (`src/config/policy-artifact-read.ts`).
- **IP literals and wildcards:** `*` in a domain rule never matches an IP literal in any spelling, so a fetch or git destination given as an IP literal escalates unless a rule names it. A fetch of a local name (`localhost`, `*.local`, `*.internal` and similar) or of a cloud-metadata name or address is denied outright (`src/trusted-process/domain-utils.ts`); other loopback and private addresses are refused at connect time by the fetch server's own guard (§2c).
- **Deterministic lint at every compile choke point** (`src/pipeline/policy-lint.ts`): rejects server-wide allows, conditions on roles they cannot constrain, unconstrained mutation allows, allows of tools a server marks as changing state, write/delete allows within `~` or broader, and `*` or public-suffix wildcard domains (`src/types/public-suffix.ts`) unless the constitution or `--allow-broad-domains` opts in (`src/pipeline/compile.ts`). Read breadth is intentionally not linted. `refresh-lists` does not run the lint.
- **Verification:** the verifier (`src/pipeline/policy-verifier.ts`) has a model generate test scenarios from the constitution, runs them through a real policy engine and has the same model judge the results. Unless `policyVerifierModelId` names another model, that model is the policy model itself, in a separate session (`createPipelineModels` in `src/pipeline/pipeline-runner.ts`). The verdict rests on the judge's structured pass flag and the engine's results. A judge correction that would newly expect `allow`, or that touches a handwritten scenario, is never applied automatically, and every scenario is replayed against the current rules before a server passes (`src/pipeline/pipeline-runner.ts`). The handwritten invariant scenarios (`src/pipeline/handwritten-scenarios.ts`) are verified in every compile: global, persona and job. `ironcurtain doctor` replays the recorded decisions against the current engine (`src/policy-artifacts/scenario-replay.ts`).
- **Fail-closed loading:** compiled policies, dynamic lists and annotations are schema-validated on load (`src/types/policy-schema.ts`); a typo fails the load instead of widening a rule, and the engine denies an unknown decision. Provenance and staleness are checked at session start, at workflow hot-swaps and by `ironcurtain doctor` (`src/config/policy-provenance-check.ts`, `src/policy-artifacts/provenance.ts`); `policy.onStale: "refuse"` (opt-in) refuses a stale policy instead of warning.
- **Locked, audited persona compiles:** CLI and web UI persona compiles share one path that holds the compile lock, runs the broad-policy validator and writes an audit record (`runPersonaCompile` in `src/persona/persona-compile-service.ts`). Cron jobs run only under the policy compiled from their own (or their persona's) current constitution; a missing or stale policy refuses the run, with no fallback (`src/cron/job-policy.ts`). A policy directory is loaded only when it canonically is one of the directories IronCurtain compiles policies into (never an agent-writable tree such as a session sandbox, workspace or workflow run) and no other local user can change it (`src/config/validate-policy-dir.ts`).
- **Mediated list resolution:** data-backed dynamic lists are resolved by an LLM whose MCP calls go through the security kernel with the bundled read-only policy: escalations are denied, every call is audited, only the server the list names is connected, and network-egress servers cannot back a list (`src/pipeline/proxy-mcp-connections.ts`). A user's manual removals survive recompiles and refreshes (`src/pipeline/list-resolver.ts`).
- **Restrictive dynamic lists:** missing, empty, legacy or incompletely validated lists cannot silently narrow an escalation or deny rule. Other predicates remain in force; allow/assess rules retain concrete matching. Completeness survives persistence, merge and cache hashing; manual additions do not repair prior validation loss.
- **Human review:** compiled policy is a build artifact meant to be reviewed like firewall rules. Constitution customization, persona generation/show and cron confirmation display every policy line with controls and invisible formatting escaped. Diff styling is applied only after escaping; model questions, summaries, progress and errors use the same terminal boundary. Stored policy text is unchanged (RV-20).

**Residual risk:** The shipped tool annotations carry no MCP side-effect hints yet, so the lint's `side-effect-tool-allow` check finds nothing for them; remote mutations on `github` and `google-workspace` are not identified by it. The verifier is still an LLM, and by default the model that wrote the rules, so it can share the compiler's misreading of the constitution; `policyVerifierModelId` makes it a different model. A rule that satisfies the schema, the scenarios and the judge can still be too broad in a way the lint does not cover. Resolved list values are not confirmed by a human before they are written (list poisoning). In Docker Agent Mode, protected files inside the workspace are reachable through the bind mount.

## 2. Execution Containment Limitations & Escapes

IronCurtain has two session modes with different containment models. Both use the MCP proxy (the trusted process, `src/trusted-process/tool-call-coordinator.ts`) as the policy enforcement boundary; the agent-side sandbox differs.

### 2a. Code Mode (Builtin Agent) — V8 Isolate

**Risk:** The builtin agent runs LLM-generated TypeScript in a V8 isolate. V8 isolates are a weaker boundary than OS-level virtualization or containerization (gVisor, Firecracker).
**Vectors:**

- **V8 zero-days:** a V8 vulnerability could let agent code escape into the host Node.js process.
- **Resource exhaustion:** memory, CPU or console floods against the host process.
- **Side channels:** timing attacks might leak information about the host.

**Mitigation:**

- **Fresh isolate per script:** every `execute_code` script runs in a new isolated-vm isolate that is disposed when it ends (`src/sandbox/code-mode-chain.ts`). The isolate has no `process`, `require` or Node.js built-ins; it sees only synchronous tool stubs, so it cannot spawn processes or open network connections itself. The script runs as the body of an async function, but each stub call blocks the isolate until the host settles it, and the host routes the call in-process, with no stdio or subprocess hop, to the coordinator's policy pipeline before any MCP relay sees it (`src/sandbox/ironcurtain-protocol.ts`).
- **Host-enforced limits** (`src/sandbox/chain-limits.ts`): a 128 MB heap limit per isolate, at most 1 MiB and 10,000 entries of console output (counted on the host), two concurrent scripts per builtin session (four per Docker Code Mode proxy) with a bounded queue, and a process-wide memory budget shared by every sandbox in the process. Closing a session or aborting a turn disposes the isolate and withdraws its pending tool calls.
- **Budgets:** tokens (cache reads and writes included), steps, wall-clock time and list-price cost are limited per turn and reset when the agent returns control; exhaustion ends the turn with `BudgetExhaustedError` (`src/session/resource-budget-tracker.ts`).

**Residual risk:** A V8 or isolated-vm escape runs as the host user. Builtin budgets are per turn, so a long multi-turn session has no cumulative cap.

### 2b. Docker Agent Mode (External Agents) — Container Isolation

**Risk:** External agents (Claude Code, Codex, Goose) run in containers and control their own execution loop. IronCurtain mediates only their external access: MCP tool calls and network traffic.
**Vectors:**

- **Container escapes:** a vulnerability in the container runtime or the kernel.
- **Abuse of in-container privilege:** the agent is root-capable inside the container by default (see below).
- **Resource exhaustion:** CPU, memory, processes or disk inside the container.

**Container posture, Docker runtime, default settings** (`src/docker/agent-privileges.ts`, `src/docker/docker-manager.ts`, `buildAgentContainerConfig` in `src/docker/docker-infrastructure.ts`):

- **Capabilities:** `--cap-drop=ALL`, then SETUID, SETGID, CHOWN, FOWNER, DAC_OVERRIDE, AUDIT_WRITE are added back (`AGENT_SUDO_CAPABILITIES`) so `sudo apt-get install` works. No `no-new-privileges`.
- **Passwordless sudo:** the agent images grant the `codespace` user `NOPASSWD:ALL` (`docker/Dockerfile.base.arm64`; the x86 base inherits it from the devcontainers universal image), so the agent can become root inside the container at any time.
- **Start user:** on Linux Docker the container starts as `0:0`, so `docker/entrypoint-uid-remap.sh` can renumber `codespace` to the host UID and GID before dropping to it. IronCurtain refuses to run Linux Docker agent mode as host root (`src/docker/container-identity.ts`).
- **Container root can be host root:** on native Linux Docker without rootless mode or userns-remap, container UID 0 is host UID 0 on every bind mount, so a compromised agent can leave root-owned or setuid files in the workspace (a git hook, a `node_modules/.bin` entry, a build tool) that a later host command runs as root. IronCurtain logs a warning once per bundle (`HOST_ROOT_EXPOSURE_WARNING` in `src/docker/docker-infrastructure.ts`), `ironcurtain doctor` reports it (`checkDockerUserNamespace` in `src/doctor/checks.ts`), and the host scans the read-write host mounts after each turn, at session end (PTY sessions: only then), after a failed start and after dependency provisioning (`src/docker/host-mount-privilege-scan.ts`). The scan never follows a symlink; it strips setuid and setgid bits from files the host user owns and reports what it cannot change (root-owned or another user's files), for removal with sudo. Rootless Docker and userns-remap do not yet work with the Linux UID remap. Startup, provisioning and recovery teardown findings are delivered even if setup fails. Completed jobs preserve notices; the current page keeps the newest twenty distinct host-file warnings until dismissed. RPC refreshes retain them; full page reloads and new clients use persisted logs. These notices do not provide containment.
- **Read-write mounts:** the workspace at `/workspace` (`src/docker/container-workspace.ts`; read-only for `workspaceAccess: read-only` workflow states); the proxy sockets directory at `/run/ironcurtain` (Linux) or the two socket files (Apple `container`); the agent CLI's conversation-state directory (`/home/codespace/.claude/`, `/home/codespace/.codex/` or Goose's sessions directory, `src/docker/conversation-state.ts`); the workflow dependency layers at `/opt/workflow-venv` and `/opt/workflow-node_modules` (`src/docker/workflow-dependency-cache.ts`; read-only in read-only scopes); and, on Apple `container` when nested Docker is admitted, its registry and package egress sockets (`buildDockerWorkloadEgressMounts`, §2d). Read-only: `/etc/ironcurtain` (orientation files and the public session CA), the apt proxy configuration, staged skills and scripts.
- **Opt-in `agentSudo: false`** (`src/docker/agent-privileges.ts`): the container starts as the image's numeric agent UID, keeps no added capabilities and runs with `--security-opt no-new-privileges:true`, so the agent cannot create root-owned files or write host files it does not own. apt and the system trust store are unavailable; tools trust the session CA through `SSL_CERT_FILE`, `NODE_EXTRA_CA_CERTS` and similar variables. It is refused, not silently weakened, on Apple `container`, together with nested Docker, and on Linux Docker unless IronCurtain runs as UID 1000.
- **Dependency-tree verification:** host-side workflow dependency manifests stop above 100,000 entries, 64 directory levels, 16 GiB of content or 64 MiB of entry metadata. Streaming directory iteration and bounded file reads reject growth during hashing. These verification bounds do not impose provisioning-time disk/inode quotas (`src/docker/workflow-dependency-cache.ts`).
- **Host-side batch parsing:** combined stdout and stderr above 4 MiB are rejected before adapter parsing, without truncating JSON or retrying as empty output. Goose uses the linear terminal-sequence scanner. Container storage/provisioning diagnostics and workflow stderr are rendered as bounded visible text before terminal display. This parsing bound does not replace container process or output-capture limits.
- **Resource limits** (`src/config/user-config.ts`, `src/docker/resource-limits.ts`, `src/docker/docker-manager.ts`): by default 8192 MB of memory (`--memory-swap` equal to `--memory`, so no swap), 4 CPUs and 4096 PIDs (`dockerResources`; each can be set to null for no limit, and memory and CPUs are clamped to the host), plus `--ulimit nofile=65536` (`AGENT_OPEN_FILES_LIMIT`). Apple `container` VMs get the memory and CPU limits; the PIDs and open-files limits are Docker-only.

**Network isolation per backend** (`resolveNetworkTopology` in `src/docker/network-topology.ts`):

- **Linux Docker (`uds`):** `--network none`. The MCP and MITM proxies are Unix sockets in the bind-mounted sockets directory (`buildUdsSocketMounts` in `src/docker/docker-infrastructure.ts`); the entrypoint bridges `127.0.0.1:18080` to the MITM socket with socat (`docker/entrypoint-claude-code.sh` and its Codex and Goose twins).
- **macOS Docker Desktop (`tcp-sidecar`):** the agent runs on an `--internal` network with no default route. A sidecar container bridges exactly the two proxy ports to the host's loopback-bound proxies. The sidecar image is built locally from `docker/transport-sidecar/Dockerfile` and run by immutable image ID, read-only, as `nobody`, with every capability dropped and `no-new-privileges`, limited to 64 MB, 0.25 CPU, 64 PIDs and 256 open files (`src/docker/transport-sidecar-image.ts`, `TRANSPORT_SIDECAR_LIMITS`). Session setup aborts if the proxies are unreachable from the container (`checkInternalNetworkConnectivity`).
- **Apple `container` (`uds`, container CLI 1.2.1 or later on macOS 26+, Apple silicon):** each container is its own lightweight VM, created with `--network none`, so the VM has only a loopback interface. Each proxy socket file is mounted with `-v`, which makes the runtime create a vsock relay for it; the sockets are mode 0666 inside a 0700 host directory, because the relay propagates the host mode bits and the in-VM owner is root (`src/docker/docker-infrastructure.ts`). The 1.2.1 floor exists because 1.2.0 applies masked and read-only `/proc` paths that break nested Docker and 1.2.1 is the first release that can opt out (`src/docker/apple-container-manager.ts`). The host-only vmnet topology with `0.0.0.0` listeners (`tcp-hostonly`) is retained in the code but no backend selects it.
- **Nested Docker sessions** change the picture: see §2d.

**Session CA:** the MITM CA key stays on the host (`src/docker/ca.ts`, mode 0600 in a 0700 directory). Only the public certificate enters the container, through the read-only orientation mount, and the entrypoint installs it into the system trust store at startup (`docker/entrypoint-uid-remap.sh`); the image itself is CA-neutral.

**Residual risk:**

- With sudo on, the agent is root inside its container: it can rewrite binaries, the dependency layers and its CLI's configuration, and it has more kernel attack surface for an escape attempt than a capability-less process.
- The turn-time privilege scans race processes the agent left running in the container; only the scan after the container is removed is authoritative. Root-owned setuid files can only be reported, not neutralized, by the non-root host process.
- Apple `container` has no runtime egress probe for the `uds` topology; like Linux `--network none`, it relies on the runtime.

### 2b-i. Dynamic Domain Expansion and Passthrough Egress (Docker Agent Mode)

**Risk:** The agent can ask for new internet destinations at runtime with the `add_proxy_domain` virtual MCP tool. Unlike provider hosts, which get a TLS-terminating MITM path with credential swap, endpoint filtering and request sanitizing, an approved destination gets a **passthrough tunnel**: traffic is relayed without content inspection and without credential injection.
**Vectors:**

- **Exfiltration through an approved domain:** the agent gets a domain it controls approved and sends workspace data through it.
- **SSRF:** an approved name resolves to an internal or metadata address.
- **Long-lived channels:** WebSocket and other tunnels held open for a sustained exfiltration channel.
- **Domain confusion:** `api-weather.com` instead of `api.weather.com`.
- **CDN fronting:** an approval for one tenant of a shared edge used to reach another.

**Mitigation:**

- **Human-only escalation:** `add_proxy_domain` is a hardcoded `escalate` rule marked `humanOnly` (`proxyPolicyRules` in `src/docker/proxy-tools.ts`). The pipeline never sends it to the auto-approver, never matches or offers it as an `/approve+` whitelist pattern, and leaves it pending under "approve all" (`src/trusted-process/tool-call-pipeline.ts`). The mux, listener and CLI render the domain and justification escaped and in full (§6). Removing a domain is allowed.
- **Validation before policy evaluation:** the domain argument is validated before the policy engine, an approver or the auto-approver sees it (`validateProxyToolArguments` in `src/trusted-process/tool-call-pipeline.ts`, `parsePassthroughTarget` in `src/docker/proxy-tools.ts`). IP literals in any IPv4 spelling, wildcards, `localhost`, `*.docker.internal`, local and metadata names, malformed text and ports other than 443 and 80 are denied as `invalid-arguments` and audited.
- **One host on one port:** an approval covers `host:443` (default) or `host:80` (on request), nothing else. A 443 tunnel is relayed only after the client's TLS ClientHello names the approved host in its SNI (read with a 64 KiB, 64-record, 10-second bound, `src/docker/tls-client-hello.ts`); a client that sends no SNI is refused. A port-80 tunnel is served as HTTP with each request re-originated to the approved host, so the Host header cannot name another site (`src/docker/mitm-proxy.ts`).
- **Address screen:** non-public IP literals and local or metadata names are refused before a tunnel is acknowledged, and names are dialed through a guarded lookup that refuses an answer set with any private, loopback, link-local or metadata address (`createGuardedLookup` in `src/net/address-policy.ts`, used by `src/docker/mitm-proxy.ts`). The shared address policy classifies an IP literal by the address it denotes, embedded IPv4 included, and refuses cloud-metadata names and addresses under every policy. Each address policy keeps its own keep-alive pool, so a socket opened for a trusted private LLM gateway never serves a passthrough request (`src/docker/outbound-transport.ts`).
- **Bounded tunnels:** raw tunnels and plain-HTTP WebSocket bridges close after 10 minutes without traffic, port-80 tunnels after 15 minutes without traffic, and each bundle's proxy caps concurrent tunnels at 64 (`src/docker/mitm-resource-limits.ts`). Revoking an approval tears down every tunnel opened under it.
- **Session-scoped:** approvals live in the bundle's MITM proxy memory and are never written to disk. In a shared-container workflow the bundle spans several states, so an approval outlives a persona swap (`src/docker/mitm-proxy.ts`).
- **Audit:** every `add_proxy_domain` call, with domain and justification, is in the session audit log. With taint escalation on (§4), an approved passthrough destination taints the session (`src/trusted-process/audit-log.ts`, `src/trusted-process/taint-policy.ts`).
- **Opt-in policy-evaluated egress** (`egressPolicy.enabled`, `src/trusted-process/egress-policy.ts`, `docs/designs/mitm-egress-policy.md`): every destination that is not a provider or registry is decided by the session's policy as a `network/request` call. Hosts in `egressPolicy.allowedHosts` (`*`, `*.example.com`, `host`) are allowed; everything else escalates to a human (human-only, decided once per `host:port`). Only ports 443 and 80 and only names (no IP literals, local or metadata names) are admitted, and every decision is audited.
- **Deprecated escape hatch:** `IRONCURTAIN_MITM_ALLOW_ALL_HOSTS=1` tunnels every unknown host (any port) without egress filtering, after the same address screen. It prints a deprecation warning at every proxy start and is ignored while `egressPolicy.enabled` is on (`src/docker/mitm-proxy.ts`).

**Residual risk:** Once a destination is approved, its traffic is unmediated: the proxy cannot tell an API call from exfiltration. Treat an approval as granting the agent internet access to that host. The SNI pin cannot see past Encrypted ClientHello: a hello whose outer SNI is the approved host is relayed and logged, and its inner name is invisible to the proxy. Host-header fronting inside an encrypted 443 session is left to the origin's own checks.

### 2b-ii. Package Installation Proxy (Docker Agent Mode)

**Risk:** Agents install packages (npm, PyPI, Debian APT, crates.io) from public registries inside the container. A compromised or typosquatted package runs code inside the container, with root available through sudo by default.
**Vectors:**

- **Supply chain attack in-container:** install scripts run with the agent's container privileges.
- **Quarantine bypass:** a malicious version published recently slips through a short age gate or a broad allowlist.
- **Registry writes and accounts:** publishing, dist-tag moves or yanks with the user's or an attacker's token; registry APIs used as an exfiltration channel.

**Mitigation** (`src/docker/registry-proxy.ts`, `src/docker/package-validator.ts`):

- **Read-only:** only bodiless GET and HEAD requests are forwarded (`checkRegistryRequestMethodAndBody` in `src/docker/registry-request-gate.ts`). Publishes, dist-tag writes, crate publishes and yanks, logins and npm audit POSTs get a 403. Containers set `NPM_CONFIG_AUDIT=false` and `NPM_CONFIG_FUND=false` (`src/docker/package-client-env.ts`).
- **Credentials stripped:** only content-negotiation, caching and range headers reach upstream (`READ_ONLY_REQUEST_HEADERS` in `src/docker/registry-request-gate.ts`); `Authorization`, `Cookie`, `npm-*` and every other header are dropped.
- **Route allowlist** (`classifyRegistryRoute` in `src/docker/registry-proxy.ts`): npm packuments and tarballs plus `/-/ping`, `/-/v1/search` and `/-/package/<name>/dist-tags`; pypi.org `/simple/<name>/` and the JSON API; files.pythonhosted.org `/packages/...`; Debian `.deb` files and allowlisted `dists/` metadata; index.crates.io sparse-index files and `/config.json`; static.crates.io `/crates/...`; crates.io crate downloads and `cargo search`. Everything else is refused with 403.
- **Canonical paths:** a request path that has more than one reading is refused before parsing: a segment that starts with a dot (dot segments in any spelling included), backslashes, empty segments, a percent-encoded `.`, `\`, `%`, `?` or `#`, an encoded `/` anywhere but npm's `@scope%2fname`, and control or non-ASCII characters (`src/docker/registry-request-path.ts`). The denylist is matched against the canonical, percent-decoded package name; for PyPI that is the PEP 503 name (`normalizePypiName` in `src/docker/registry-proxy.ts`).
- **Quarantine age gate:** a version must be at least 2 days old by default (`packageInstall.quarantineDays`); the denylist wins over the allowlist, and an allowlisted package skips the gate; other packages with missing or unavailable metadata are denied. The PyPI gate applies per distribution file, so a new wheel added to an old release is quarantined (`src/docker/package-validator.ts`, `src/docker/registry-proxy.ts`).
- **Bounded metadata handling:** per proxy at most 8 concurrent metadata operations, 256 MiB held, 128 MiB per response and a 5-minute deadline (`src/docker/registry-metadata-budget.ts`).
- **Audit:** every forwarded or refused registry request is written to `package-audit.jsonl` in the session directory with method, host and path (`src/docker/package-types.ts`).

**Residual risk:**

- Debian `.deb` files skip the age gate (they are validated with an epoch publish date, so only the allow and deny lists apply).
- The PyPI JSON API is forwarded unfiltered (it lists every release); the download path still enforces the gate on the file itself.
- List entries are not normalized: a PyPI name is compared in its PEP 503 form (lowercase, every run of `-`, `_` and `.` as one `-`), so a `deniedPackages` entry `typing_extensions` never matches; write `typing-extensions`.
- Install scripts of an allowed package run with the agent's privileges (root through sudo by default) and can reach anything the container can reach.
- Read-only registry requests still carry request paths and timing to the registry.

### 2c. OS-Level MCP Server Sandboxing (Both Modes)

**Risk:** MCP server processes run on the host and could be exploited through crafted tool calls or responses, or be compromised themselves (a poisoned npm package, a malicious image).
**Mitigation:**

- **Per-server sandbox disposition** (`src/config/mcp-servers.json`, `src/trusted-process/sandbox-integration.ts`): `filesystem`, `git` and `google-workspace` run under `srt` (`@anthropic-ai/sandbox-runtime`: bubblewrap on Linux, Seatbelt on macOS). `fetch` and the memory server run unsandboxed on the host (`sandbox: false`); `github` runs in Docker and is not wrapped in `srt`. The table in [SANDBOXING.md](../SANDBOXING.md#layer-4-os-level-sandbox-bubblewrapsrt-both-modes) gives the details per server.
- **Fail closed by default:** `sandboxPolicy` defaults to `"enforce"` on Linux and macOS (`src/config/sandbox-policy.ts`): a server that asks for an OS sandbox does not start when bubblewrap, socat or ripgrep is missing, the platform is unsupported, or srt cannot start a sandbox on the host (one srt test run per process, `resolveOsSandboxAvailability`); other servers keep running. `"warn"` is an explicit opt-out that starts the server unconfined with a visible warning. Audit entries record `sandboxed: false` for a server that runs without the sandbox it asked for. The tool listings of `annotate-tools`, `compile-policy` and `mcp add` launch servers the same way (`src/trusted-process/tool-listing-launch.ts`).
- **Read-containment baseline:** every sandboxed server's `denyRead` is unioned with the IronCurtain home, the relays' per-user scratch root (`<os.tmpdir()>/ironcurtain-<uid>`, created 0700 and owner-checked, `src/trusted-process/spawn-cwd.ts`), the configured `credentialProtection.extraPaths`, trusted environment-file paths, all effective/default/XDG Anthropic CLI credential candidates, and the fixed host credential stores (`BASELINE_CREDENTIAL_DENY_READ`: the default-named SSH private keys `~/.ssh/id_*`, `~/.aws`, `~/.gnupg`, `~/.config/gcloud`, `~/.docker/config.json`, `~/.git-credentials`, `~/.npmrc`, `~/.config/gh`, `~/.kube/config`, `~/.claude/.credentials.json`, `~/.codex/auth.json`; every store the policy engine protects except `~/.netrc` and the rest of `~/.ssh`), the shell startup files where API keys are often exported (`~/.bashrc`, `~/.bash_profile`, `~/.bash_login`, `~/.profile`, `~/.zshrc`, `~/.zshenv`, `~/.zprofile`, `~/.config/fish`) and a `.env` left in IronCurtain's package root (the relays' working directory). A server can re-open a credential entry only by naming it exactly in its own `allowRead`. No configuration can re-open any other part of the IronCurtain home or the scratch root: a server gets back only the session sandbox and its own working and credential directories.
- **Filesystem server confinement:** the filesystem server runs with `confineToRoots`: the home directory, the temporary directories and the runtime directory are hidden, and its MCP roots are re-exposed when they change, with the backend restarted (`src/trusted-process/roots-confinement.ts`). Roots it cannot be given are refused (`root-not-exposable`). Approved roots are canonical, captured when the escalation is raised, re-checked after the approval wait and verified against the backend, and a mismatch drops the connection (`src/trusted-process/roots-expansion.ts`).
- **Allowlisted child environments:** relays and backends no longer inherit the host environment (`src/trusted-process/child-env.ts`). They get a fixed allowlist (paths, locale, proxy and CA settings, version-manager roots, Docker CLI connection settings); a server's `-e NAME` arguments forward only the variables it declares; `SSH_AUTH_SOCK` goes only to the git backend; `NODE_OPTIONS`, `NODE_PATH`, `LD_*` and `DYLD_*` are never passed. Each relay receives only its own server's configuration and credentials.
- **fetch SSRF guard:** the unsandboxed fetch server resolves each name once, requires the whole answer set to be public, connects only to a checked address, refuses local and metadata names, screens IP literals in every spelling, follows at most 5 same-origin redirects (re-validating each hop) and returns cross-origin redirects to the agent instead of following them (`src/servers/guarded-fetch.ts`). Private destinations are reachable only with the opt-in `fetch.allowPrivateNetworks`, and only when the URL names them literally.
- **Pinned launches:** the filesystem server is an exact-pinned dependency started with `node`, never `npx`; every backend runs in a private per-server working directory, never the launch directory (`src/trusted-process/spawn-cwd.ts`).

**Residual risk:**

- `fetch` and the memory server run with the host user's privileges and network access (fetch's guard is its own code); `github` is contained only by Docker. `google-workspace` is still launched with `npx`.
- Servers a user adds (`ironcurtain mcp add`, `src/config/mcp-servers-overlay.ts`) can only get the `none` argument role, so no protected-path, containment or domain check applies to their arguments, and one with `sandbox: false` runs uncontained (annotating it too).
- The read-containment baseline does not hide `~/.netrc` (git over HTTPS may authenticate with it), shell history files, project `.env` files, SSH private keys under names other than `~/.ssh/id_*` from sandboxed servers.
- MCP roots narrow what the filesystem server can reach, but the policy check of a path and the server's use of it remain separate steps (a validate-then-use window inside the approved roots); a server that cannot report its roots cannot be verified; and a human can approve a broad ancestor root.

### 2d. Nested Docker Workloads (Docker Agent Mode, opt-in)

**Risk:** With `dockerWorkload.enabled`, a Docker agent session gets a private Docker daemon (see [CONFIG.md](../CONFIG.md#nested-docker-workloads)). The agent has Docker administrator authority over that daemon, and the daemon needs kernel features ordinary agent containers never get.
**Accepted risks, Docker Desktop backend (macOS and WSL2):**

- **Kernel and seccomp surface:** the nested daemon runs rootless in a sidecar container with only SETUID and SETGID added (`DOCKER_DESKTOP_SIDECAR_CAP_ADD` in `src/docker-workload/docker-desktop-sidecar.ts`). Its seccomp profile is Moby's default plus unconditional allows for `clone`, `mount`, `pivot_root`, `sethostname`, `setns`, `unshare` and `umount2` (`src/docker-workload/nested-daemon-profile.ts`), checked against the reviewed ceiling `config/docker-workload/profile-ceiling.json` by `test/docker-workload/profile-ceiling.test.ts`. This exposes user-namespace kernel attack surface (the class of `nf_tables` privilege escalations) to a possibly compromised agent.
- **Mask exceptions:** the sidecar runs with `systempaths=unconfined` (no masked or read-only `/proc` paths) and, in the online modes, gets `/dev/net/tun` (`src/docker-workload/docker-desktop-sidecar.ts`).
- **Shared VM:** every Docker Desktop session's daemon runs on the one Docker Desktop Linux VM and kernel, shared with other sessions and other workloads. A kernel escape from one session reaches the others (`src/docker-workload/docker-desktop-sidecar.ts`).
- **Network:** online nested sessions attach the agent and the daemon to isolated `--internal` relay networks whose only exits are fixed-target relays to guarded host listeners (`src/docker-workload/desktop-relay.ts`); on WSL2 the agent runs on that network instead of `--network none`.
- **Relay credential:** the host-hop proxy credential is passed through the Docker CLI's allowlisted private environment using a value-free `--env` argument, then consumed from a fixed environment name by the relay. Neither host nor container command arguments carry it (RV-29). Privileged access to `docker inspect` still reveals the relay environment; the untrusted bundle receives neither that environment nor the outer Docker socket.
- **Go builder identity:** nested-daemon and relay stages pin `golang:1.26.11-bookworm` by its verified multi-platform index digest (`docker/nested-daemon/Dockerfile`, `docker/nested-relay/Dockerfile`). The toolchain check also verifies supported patch versions. Reproducible host builds and registry metadata do not substitute for runtime qualification of the resulting images.

**Accepted risks, Apple `container` backend:** the daemon runs in the agent's own VM (one VM per session, so no kernel is shared with other sessions). The agent container of a nested session alone runs with a fully visible `/proc` (`APPLE_FULLY_VISIBLE_PROC_ARGS` in `src/docker/apple-container-manager.ts`), which a nested container needs to mount its own procfs. Nothing under `/proc` is masked or read-only in that container. The agent holds neither CAP_SYS_ADMIN nor CAP_NET_ADMIN, but many sysctls check only file permissions, so container root (through sudo) can change kernel settings of the session's VM through `/proc/sys`. The VM, which runs only this session, is the boundary that holds.

**Both backends:**

- **Egress non-claims:** `packages` mode lets any process in the session send bounded workspace or build data to the fixed public package repositories through allowed package paths, request metadata and timing ([CONFIG.md](../CONFIG.md#nested-docker-workloads)); `images` and `offline` remove that route (`src/docker/package-egress-proxy.ts`, `src/docker/registry-egress-proxy.ts`). Package and image contents remain untrusted.
- **Disk is observed, not quota-limited:** the watchdog measures what the bundle actually grows (an Apple VM's rootfs image blocks; on Docker Desktop the daemon volume's Engine-reported size plus a free-space floor on the VM disk) and revokes the bundle past its thresholds (`src/docker-workload/observed-storage.ts`, `src/docker-workload/resource-watchdog-supervisor.ts`). The Engine's apparent size can under-report sparse files and renames, so on Docker Desktop the adversarial guarantee is the VM disk floor.
- **Image provenance:** the nested daemon's Docker toolchain image is pulled by its versioned tag, and the build then uses the digest the local engine resolved (trust on first pull, not a reviewed digest; `src/docker-workload/toolchain-source.ts`).

## 3. Trusted Process Surface Area

**Risk:** The trusted process parses structured data from the untrusted agent (MCP JSON-RPC over stdio, Unix sockets or TCP).
**Impact:** A parser or validation bug could let a malformed request crash the host, bypass policy or reach a backend with unchecked arguments.
**Mitigation:**

- **Per-connection framing:** fixed-size pages and a scan cursor copy and scan input linearly, including fragmented incomplete lines. General MCP sockets cap unread input at 10 MiB; Code Mode uses 1 MiB on Unix and TCP listeners. Overflow closes only that connection; malformed lines consume the same per-turn frame budget as valid lines. Send-queue backpressure and the 64-connection listener cap remain (`src/trusted-process/socket-connection-transport.ts`, `src/trusted-process/json-rpc-read-buffer.ts`).
- **Tool argument limits** — The coordinator and MCP relay check the whole argument object before backend schema validation. The call may contain up to 4,096 nodes including the root, at a maximum depth of 32. This includes trusted tools and fields with no policy role. When the argument tree exceeds either limit, the coordinator audits the request identity and reason with an empty arguments object. Before filesystem resolution it also checks limits of 256 scalar values per role-bearing argument, 1,024 per call, 16 KiB per resource value and 256 KiB of resource characters. The in-process Code Mode bridge caps serialized arguments at 1 MiB of UTF-8 (`src/trusted-process/argument-budget.ts`).
- **Argument validation:** arguments are checked against the tool's input schema and must all be classified by the stored annotation (`unannotated-arguments`, `src/trusted-process/tool-call-pipeline.ts`). Path-role arguments reach the server as the canonical absolute path policy evaluated (`prepareToolArgs`). Role-bearing arguments with nested values always need an individual human approval (`structural-nested-argument-escalate`, `src/trusted-process/policy-engine.ts`).
- **Live schema drift:** a server whose live tool schemas no longer match the stored annotations is reported (`src/trusted-process/schema-drift.ts`, `ironcurtain annotate-tools --check`, `ironcurtain doctor`).
- **Small TCB:** relays are pure transports; policy evaluation, escalation and audit happen once, in the coordinator (`src/trusted-process/tool-call-coordinator.ts`).

## 4. Prompt Injection & "Jailbreaking"

**Risk:** The LLM follows adversarial input (from email, web pages, repository files, memory or user prompts) that overrides its instructions.
**Defense:**

- **Core design principle:** a compromised LLM is the expected threat model. The architecture does not rely on the LLM "being good".
- **Policy constraints:** a jailbroken agent can _ask_ for anything, but the policy engine decides (`src/trusted-process/policy-engine.ts`). Structural invariants cannot be influenced by agent behavior.
- **Opt-in task-scoped policy:** `--task-scoped` (for `start`, mux `/new` and `workflow start`) compiles the task text into a scope that is intersected with the session policy; out-of-scope calls escalate, and unverified task rules can only narrow (`src/trusted-process/task-scope.ts`). Never the default. Cron jobs have their own task policy, compiled from the job's task constitution, which replaces the global policy for that job (`src/cron/compile-task-policy.ts`).
- **Opt-in taint escalation** (`taintEscalation.enabled`, `src/trusted-process/taint-policy.ts`): once a session dispatches a taint source (a tool whose result can carry content other people wrote, an approved passthrough domain, an admitted egress destination), every sink call (send, post, push, share) that policy does not deny needs an individual human decision. Taint is never cleared and survives policy hot-swaps.
- **Soft mitigations:** compaction summaries are framed as data and quoted (`src/session/message-compactor.ts`), and memory output is framed as notes, never instructions (§13). These are prompt-level and model-dependent; the policy engine and escalation stay the enforcement boundary, and the auto-approver reads only the real user message.

**Residual risk:** Taint escalation does not cover content the agent reads from its own workspace or from memory, Docker traffic that never becomes an MCP call (registry downloads, configured provider hosts), or `fetch` URLs used as an exfiltration channel.

## 5. Exfiltration via Obfuscation

**Risk:** An agent allowed to send email or post comments (for example to a "safe" recipient) encodes sensitive data (base64, hex, rot13, steganography) to slip past content filters.
**Impact:** Data loss despite allowlists on recipients and destinations.
**Mitigation:**

- **Opt-in outbound content assessment** (`contentAssessment.enabled`, default off; `src/trusted-process/assessment.ts`, `src/trusted-process/assessment-detectors.ts`): deterministic detectors check the outbound-content arguments (`outbound-text`, `email-body`, `commit-message`, `fetch-url`) of calls allowed subject to assessment and of escalated calls. A finding or an error escalates to a human (human-only); it never denies and never allows on error.
- **Opt-in intelligibility check** (`contentAssessment.llmCheck`, default off, separately from the above): a cheap model judges whether content that passed the detectors is intelligible as written. It can only escalate (`src/trusted-process/assessment.ts`).

**Residual risk:** Both checks are off by default. Steganography and paraphrase are out of reach of the detectors.

## 6. Escalation Fatigue and Approval Integrity

**Risk:** Too many escalations make the user approve without reading ("click-through fatigue"); an agent shapes what the approver sees, or lands an approval on a different request.
**Impact:** A malicious action is approved.
**Mitigation:**

The mux repaints an overlay after adjacent PTY output on a covered row in the same synchronized frame. PTY cells with a different host display width from their recorded xterm width, or with invisible formatting, become styled spaces within their assigned columns. Matching wide and emoji cells remain visible; uncertain width or joining sequences cannot extend into the review dialog (`src/mux/mux-renderer.ts`).

- **High-fidelity policies:** precise compiled rules keep prompts rare (§1).
- **Faithful rendering:** the mux picker, the escalation listener and the builtin CLI banner render every argument escaped (JSON-quoted, control, C1, bidi and invisible characters as `\u` escapes) and in full (`src/terminal/display-sanitize.ts`). The web UI shows every invisible or direction-changing character in an argument as a highlighted escape (`packages/web-ui/src/lib/components/ui/safe-text/safe-text.svelte`) and renders agent markdown without raw HTML, styles or non-web links (`packages/web-ui/src/lib/markdown.ts`).
- **No focus stealing, armed decisions:** the mux picker never opens on its own (a bell, badge and banner announce an escalation; Ctrl-E opens the picker), and a decision counts only after the request has been drawn in full for 1 second (`ESCALATION_ARMING_DELAY_MS` in `src/mux/escalation-picker-state.ts`). The web UI arms the approval buttons of the modal, the Escalations page and the workflow escalation panel only after 750 ms in place (`ESCALATION_ARM_DELAY_MS` in `packages/web-ui/src/lib/components/features/escalation-modal.svelte`), and a new escalation does not take keyboard focus. Decisions are bound to the escalation id that was shown.
- **Bulk approval only for what was shown:** `/approve all` in the mux opens a screen listing every pending escalation and approves exactly that set; the standalone listener requires a confirmation code tied to the listed set (`src/escalation/listener-command.ts`). Human-only escalations are never covered.
- **Bounded browser review:** list/detail/push records are complete within 16 KiB or explicitly deny-only. Server approval paths check original records, including every group member before any resolution. Failed RPCs preserve held reviews with visible errors; unreadable workflow details block gate approval. The 8 MiB aggregate response cap can still reject very large lists, without aborting unrelated refreshes.
- **Grouped approval** (`src/escalation/escalation-groups.ts`; `/approve group N` in the mux and listener, the web UI's group review): escalations that share one whitelist pattern can be approved together, behind a confirmation screen that lists the group; any change to the group cancels it. There is no summarization.
- **Opt-in AutoApprover** (`autoApprove.enabled`, off by default; `src/trusted-process/auto-approver.ts`): a cheap model may approve an escalation when the user's most recent message clearly authorizes it. It sees the user's message as the only trusted input and the call as a JSON-encoded data block; URL and git arguments appear only as validated hostnames, and named remotes as where they really connect. Before any model call, a deterministic anchor check requires every escalated path (or its directory), verified host and identifier to appear in the user's message. It can only return approve or escalate, never deny, and errors escalate. It is never consulted for human-only escalations, and it is off for workflows. System-generated turns (memory auto-save) clear the user context.
- **Approval whitelisting** (`src/trusted-process/approval-whitelist.ts`): `/approve+` whitelists the exact canonical path of each approved path for the rest of the session. A directory-wide pattern (the parent directory, recursively) is an explicit second choice: `/approve+dir N` in the listener, `W` in the mux picker, or the second option in the web UI and workflow prompts. It is never chosen in bulk and never offered for `/`, the home directory or its ancestors, or in or around `~/.ssh`, `~/.aws`, `~/.gnupg`, `~/.config`, `~/.local`, their macOS counterparts under `~/Library`, relocated XDG directories or the host credential stores. A pattern must constrain every role that escalated; zero-constraint candidates are refused, not offered with a warning. Domain constraints bind resolved destinations (a named git remote binds to where it connects), and a path swapped for a symlink ends the match. Patterns only turn escalate into allow, never override deny, and are never persisted.
- **Policy learning:** repeated human approvals produce deterministic amendment proposals (after 3 approvals of one pattern) that the customize-policy flows show as a diff and apply only when the user accepts them; they take effect after a recompile (`src/audit/amendment-proposals.ts`). Nothing is applied automatically.

**Residual risk:** Quorum or two-person approval is **not implemented**. A user who approves a directory-wide pattern approves everything below it for the session.

## 7. Sandbox Persistence & Session Resumption

**Risk:** Session sandboxes persist under `~/.ironcurtain/sessions/` and can be resumed. A compromised agent leaves artifacts that re-compromise it when the session resumes.
**Impact:** A one-time prompt injection persists across resumptions.
**Context:** This is expected: persistence enables long tasks. The policy engine enforces every invariant on resumed sessions, so the blast radius is that of the original session.

- **Agent-writable state is read defensively:** the conversation-state directory is mounted read-write, so everything in it is agent-controlled and persists into resumes and later shared-container workflow states. Host code never follows links there, opens non-regular entries or walks it unbounded: `CLAUDE.md` is replaced atomically and the transcript probes are bounded and never open files (`src/docker/conversation-state.ts`, `src/hardened-fs.ts`). Agent-reported Codex thread ids are accepted only as UUIDs.
- **Builtin conversations:** `messages.jsonl` holds the full builtin conversation including tool output; it is written with mode 0600, atomically and without following links, and must validate completely on load (`src/session/conversation-store.ts`).
- **Retention:** `ironcurtain prune` removes sessions and workflow runs inactive for 30 days by default; automatic pruning is opt-in (`retention.autoPrune`, `src/maintenance/prune-command.ts`).
- **One process per session:** every standalone session (builtin, batch container or PTY, fresh or resumed) holds its session's `resume.lock` while it runs, so a second resume, or a resume of a session that is still running, is refused instead of sharing its sandbox, escalations and conversation state, and a prune keeps it (`src/session/session-lock.ts`).
- **Restored settings fail closed:** a resume restores the persona, workspace, policy directory, task scope and `disableAutoApprove` from `session-metadata.json`, and is refused when that file exists but cannot be used (damaged, truncated, not a regular file, a field of the wrong type) rather than resumed wider than the session ran (`loadResumeSessionMetadata` in `src/session/session-metadata.ts`).

**Residual risk:** A session whose `session-metadata.json` was deleted resumes like one created before metadata was recorded, without the settings it held.

## 8. Credential Leakage in Logs and the Audit Trail

**Risk:** Credentials (provider keys, OAuth tokens, `serverCredentials`) reach logs: MCP server stderr, tool arguments in the audit log, LLM interaction logs.
**Mitigation:**

- **Audit log redaction** (on by default, `auditRedaction.enabled`; `src/trusted-process/audit-redactor.ts`, applied by `src/trusted-process/audit-log.ts`): provider-prefixed keys and tokens (Anthropic, OpenAI, OpenRouter, GitHub, Google, Slack, AWS), JWTs, bearer credentials, Luhn-valid card numbers and SSNs written with dashes are masked, and the exact credential values IronCurtain holds (configured server credentials, provider API keys, OAuth tokens) are replaced wherever they appear in arguments and results.
- **Fail-closed audit:** an allowed call writes a `dispatching` record before its first side effect; if that write fails, the call is refused, and after any audit write failure the coordinator refuses further calls for the session (`src/trusted-process/audit-log.ts`, `src/trusted-process/tool-call-coordinator.ts`).
- **stderr redaction:** relays replace known credential values in server stderr with `***REDACTED***` before writing the session log: the server's stored credentials and OAuth values, and each host value of at least 8 characters that its `-e NAME` arguments forward, such as a `GITHUB_PERSONAL_ACCESS_TOKEN` exported in the shell (`backendStderrRedactor` in `src/trusted-process/mcp-proxy-server.ts`).
- **LLM interaction logs** record metadata only by default (`observability.llmInteractionLog: "metadata"`: sizes, timings, token counts, no prompt or response text), and logs are owner-only (`src/observability/private-log-file.ts`).
- **Audit report and verification:** `ironcurtain audit report` summarizes tool-call audit logs; `ironcurtain audit verify` checks the hash chain of the persona policy-mutation log (`src/audit/audit-command.ts`, `src/persona/policy-mutation-audit.ts`).

**Residual risk:** Credentials echoed by an MCP server in a tool _response_ enter the LLM context unmasked; pattern redaction misses unprefixed secrets. The policy-mutation chain is keyless: it detects accidental corruption and careless edits, not a local writer who recomputes the chain. The tool-call audit log itself is not chained.

## 9. MITM Proxy, Credential Protection and Budgets (Docker Agent Mode)

Workflow resume accepts only real run-owned `workflow-skills` and `workflow-scripts` stages. External runs require their local definition copy, and imports copy validated resources into a new local run without overwriting an existing destination. Checkpoint-selected original packages are not used for external recovery. File reads and copies pin canonical roots and use bounded no-follow operations; infrastructure revalidates scripts before dependency reads and mounting (`src/workflow/staged-directories.ts`).

**Risk:** The TLS-terminating MITM proxy (`src/docker/mitm-proxy.ts`) handles real credentials and terminates TLS for traffic from untrusted containers.
**Vectors:**

- **Credential theft or misuse:** the agent tries to read the real key, or to send its own (or an attacker's) key so the data reaches an account it controls.
- **Response header leakage:** an upstream echoes a credential in a response header.
- **Endpoint filter bypass:** a parser differential between the proxy and the upstream.
- **Provider-hosted tools:** web search, web fetch, code execution or MCP connectors run on the provider's side, outside IronCurtain's view.
- **Unbounded spend.**

**Mitigation:**

- **Credentials never enter the container:** the agent gets a 192-bit sentinel key (`src/docker/fake-keys.ts`); the real key or OAuth token exists only in the host process.
- **Credential gate** (`src/docker/provider-credentials.ts`): every credential carrier (key headers, `Authorization`, cookies, `key`/`api_key`/`access_token` query parameters) is removed; the sentinel is swapped for the real credential in the provider's configured location; any other credential gets a local 401 with no egress; a request without a credential is forwarded only to the provider's declared unauthenticated endpoints (`unauthenticatedEndpoints` in `src/docker/provider-config.ts`).
- **Strict endpoint allowlist:** only listed method and path combinations are forwarded; `*` in an endpoint glob matches only unreserved characters and never a segment of dots (`src/docker/provider-config.ts`).
- **Request sanitizers:** completion bodies are parsed (after decoding a compressed body) and provider-hosted tools, connectors and URL-sourced content are stripped or refused; a body that cannot be parsed or sanitized is answered locally with an error and never forwarded (`src/docker/request-sanitizers/`).
- **Response hygiene:** hop-by-hop and `Set-Cookie` response headers are never relayed (`sanitizeResponseHeaders` in `src/docker/egress-forwarding.ts`).
- **WebSockets refused on provider hosts:** upgrades on TLS-intercepted provider hosts are refused so every inference request passes the sanitizers, the credential gate and the budget gate (`src/docker/mitm-proxy.ts`); the Codex adapter turns WebSockets off (`src/docker/adapters/codex.ts`).
- **Response failure containment:** provider, passthrough and read-only registry relays validate upstream status codes as integers from 100 through 599 inside their asynchronous response callbacks (`src/docker/upstream-response.ts`). Invalid metadata or a callback/header failure returns 502 and closes that connection; a response already in progress is destroyed. Raw WebSocket handshake responses validate the same status range. These failures affect the exchange rather than escaping the request listener's synchronous guard.
- **Resource bounds** (`src/docker/mitm-resource-limits.ts`): per bundle at most 128 concurrent requests, 64 tunnels, 256 TLS connections, 512 client sockets and 128 MiB of buffered request bodies; request bodies are limited per provider (32 MiB by default, 50 MiB for the OpenAI and ChatGPT hosts); upstream deadlines of 10 minutes. Only the CONNECT host's leaf certificate (`src/docker/ca.ts`) is ever served, and a ClientHello naming another host is refused (`src/docker/mitm-proxy.ts`).
- **Loopback listeners:** in TCP mode (macOS Docker Desktop) the MITM and MCP proxies bind 127.0.0.1; the MITM control API requires a per-bundle bearer token that never enters the container (`src/docker/mitm-proxy.ts`, `src/docker/code-mode-proxy.ts`).

**Budgets in Docker Agent Mode** (`src/docker/budget-gate.ts`, `src/docker/docker-agent-session.ts`, `src/docker/turn-timeout.ts`):

- **Tokens and cost, host-enforced per bundle:** the budget gate admits every completion request against `resourceBudget.maxTotalTokens` and `maxEstimatedCostUsd` (defaults 1,000,000 tokens and $5, cache reads included) before forwarding it, whatever metrics lease the request carried. The request's output cap is reserved up front (32,000 tokens when it names none); usage that cannot be measured is charged a conservative estimate, never zero; cost is a list-price estimate (`src/llm-metrics/pricing.ts`), or OpenRouter's reported cost, and a prompt past a model's unlisted long-context tier (Sonnet 4.x and Opus 4.6 above 200K tokens, the Gemini Pro upper tiers) is charged twice the listed rates (`estimateCapRequestCostUsd`), as the builtin agent's budget is. The first refusal latches: the turn is stopped and the session ends with `BudgetExhaustedError`. Batch and workflow bundles forward completions only while the host runs an agent turn, so a process left running between turns cannot spend; PTY sessions (mux, web terminal) get one session-long allowance. All lanes of a shared-container workflow share one bundle budget.
- **Wall clock per turn:** `resourceBudget.maxSessionSeconds` (default 1800) bounds each turn inside the container with coreutils `timeout` on the turn's process group, a marker sweep for processes that left the group, and a longer host deadline as a backstop (`src/docker/turn-timeout.ts`).
- **Between turns:** cumulative tokens, steps (completed turns) and host-observed cost are checked before each turn. The agent's self-reported cost is display-only (`src/docker/docker-agent-session.ts`, `src/session/budget-admission.ts`).
- **Run-wide ceiling:** `settings.workflowBudget` (`maxTotalTokens`, `maxEstimatedCostUsd`, `maxWallClockSeconds`) is checked before every workflow state and fan-out lane step against the run's usage (`src/workflow/workflow-usage.ts`): the metrics bus and the sessions' host-observed cost, raised bundle by bundle to what each bundle's budget gate charged, so spend without a metrics lease, with statistics off, on an unpriced model or with unmeasured usage still counts. A session counted by neither fails both the token and the cost ceiling closed.

**Residual risk:**

- The gate reserves output only: the input of exchanges in flight can take the totals past a limit before later requests are refused. An exchange whose usage was never reported (abandoned mid-stream, or on a route the proxy does not parse) is charged an estimate, its output cap plus an input estimate from the size of the request body; text built to tokenize densely can carry more input than that estimate. Resuming a workflow mints new bundles with fresh budgets.
- The per-turn timeout bounds runaway agents, not hostile ones: an agent with sudo can replace `timeout` or escape the sweep; container teardown is the final bound. PTY sessions have no per-turn timeout.
- In TCP mode the MCP proxy endpoint on 127.0.0.1 is not authenticated, so another local process could issue tool calls evaluated under the session's policy (`src/trusted-process/tcp-server-transport.ts`). The transport sidecar's socat listens on every interface of the sidecar, including Docker's default `bridge` network, so another container on that network can reach the two forwarded ports (`src/docker/docker-infrastructure.ts`).
- The sanitizers do not make provider routes exfiltration-proof: a conversation sent to the provider can carry anything the agent read. Fields the sanitizers do not know pass through, so provider-stored context (for example an OpenAI `previous_response_id`) is outside their view (`src/docker/request-sanitizers/openai.ts`). OpenRouter web-search models are recognized by slug patterns, so a new search model passes until it is listed, and a search model the provider profile names searches on every request (`src/docker/request-sanitizers/openrouter.ts`). `anthropic-beta` values are filtered by a prefix denylist; the body rules (only client-executed tools, inline content) are the real control (`src/docker/request-sanitizers/anthropic.ts`).

**Desktop TCP admission (RV-35):** ordinary macOS Docker Desktop bundles require independent MCP and HTTP-proxy credentials at the host listeners, including health requests. A verified TLS sidecar-to-host hop protects those credentials on the shared external bridge; internal listeners use exact address/subnet binding. Desktop PTYs use native Docker exec with filtered terminal output and no published PTY port. Container creation passes secret values through the child environment, and authenticated apt files are private. Provisioning gets package-proxy access without the MCP token. Privileged Docker administrators remain trusted and can inspect container environments. See `docs/designs/docker-desktop-tcp-admission.md` for tested contracts and platform qualification limits.

## 10. OAuth Token Handling (Docker Agent Mode)

**Risk:** Docker sessions can use OAuth tokens (Claude Code, Codex) instead of API keys. `OAuthTokenManager` (`src/docker/oauth-token-manager.ts`) refreshes tokens on the host while the host's own CLI may refresh the same credential concurrently. Anthropic rotates refresh tokens, so two refreshers can invalidate each other.
**Mitigation:**

- **Re-read before refreshing:** before a refresh grant the manager re-reads the credentials file and, for macOS Keychain credentials, the Keychain; a token the host already refreshed is adopted instead (`src/docker/oauth-token-manager.ts`).
- **Atomic, rotation-aware file write-backs:** refreshed tokens are written to `~/.claude/.credentials.json`, the Anthropic CLI store or Codex's `auth.json` through a 0600 temporary file and a rename (symlinks preserved); the file is re-read after the grant, and a token the host stored meanwhile is kept and adopted (`src/docker/oauth-credentials.ts`).
- **Keychain self-refresh and write-back:** a session whose credentials came from the macOS Keychain refreshes them itself whenever they carry a refresh token: when the access token is within 5 minutes of expiry, or the provider answers 401, and neither the credentials file nor the Keychain holds a valid token by then. It writes the result back to the Keychain (`writeToKeychain` in `src/docker/oauth-credentials.ts`): the token goes on the stdin of `security -i`, never on argv, and the entry is read back and compared, so a write that did not apply is logged as a failed save while the session keeps the refreshed token in memory. This replaced the earlier read-only mode, which ended sessions at token expiry when no host CLI was running.
- **Deduplication and fallback:** one in-flight refresh is shared by concurrent callers, and a failed refresh re-reads the file once more (`src/docker/oauth-token-manager.ts`).
- **Doctor is read-only:** `ironcurtain doctor` never writes the Keychain and refreshes only with `--check-refresh`, and then only file-stored credentials (`src/doctor/oauth-checks.ts`).

**Residual risk:** No lock is shared with the host CLIs. File write-backs keep a window of microseconds between the re-read and the rename. Keychain write-backs have no keep-newer check: after the grant the entry is read only to keep its other fields (the read-back after the write only confirms the write), so if the host CLI refreshes between IronCurtain's re-read and its write, the host's newer token is overwritten, and the host CLI's in-memory refresh token may be invalid (the user has to log in again). This affects availability, not confidentiality.

## 11. SSH Agent Forwarding and Git on Agent-Writable Repositories

**Risk:** Git operations on repositories the agent can write run host `git`, and the git backend may authenticate with the user's ssh-agent.
**Mitigation:**

- **SSH agent socket for the git backend only:** `SSH_AUTH_SOCK` is forwarded to the git backend and to no other server (`src/trusted-process/child-env.ts`), and on macOS, where srt lets a sandboxed server connect only to the Unix sockets its profile names, only the git backend's profile names the canonical agent socket itself, rather than its containing directory (`writeServerSettings` in `src/trusted-process/sandbox-integration.ts`). The sandboxed git server cannot read SSH private keys at their default names (`~/.ssh/id_*`), `~/.git-credentials` or `~/.config/gh` (§2c), so it authenticates through ssh-agent; a key file under another name stays readable to it.
- **Hardened git environment:** the git backend runs with command-scope overrides for every fixed-name command key, the user's global and system credential helpers and ssh command only, no askpass, `GIT_ALLOW_PROTOCOL=https:ssh` (no `file://`, local paths, `git://` or `http://`) and `GIT_CEILING_DIRECTORIES` at the parent of the allowed directory (`src/trusted-process/git-backend-env.ts`, `src/security/git-hardening.ts`).
- **Submodules and implicit git context:** shared git environments disable implicit fetch/push/diff/status submodule recursion. Repositories with submodule metadata or named submodule configuration require per-call structural review; child repositories are not recursively inspected. `git_wrapup_instructions` needs a tracked absolute server working directory and human per-call approval; missing context denies. Git calls on a repository containing a specific protected descendant are refused, including metadata calls, without rewriting selectors. Move protected audit/config files outside the repository to enable its Git tools (RV-31).
- **Policy checks:** git remotes are resolved in-process, without running git in the agent's repository, and every fetch and push URL must pass the domain checks; compiled `domains` conditions and domain lists match where a remote connects, not what it is named. Repository configuration that changes where a remote connects (a push URL, URL rewrites, proxies, TLS trust overrides, ssh or proxy commands, a remote helper) escalates; an omitted remote is evaluated as `origin` (`src/trusted-process/git-remote-resolution.ts`). In Code Mode, writes inside `.git` escalate, and so do calls on repositories with include directives, filter/diff/merge drivers, configured hooks, alternates, redirects outside the sandbox or symbolic links inside the git directory that lead outside it, through which git would write refs, reflogs, objects or commit messages (`src/trusted-process/git-structural-rules.ts`).
- **Cron git sync** runs through a daemon-owned bare mirror and rebuilds the workspace `.git` from it before every run, so agent commits and repository configuration do not persist into the next sync (`src/cron/git-sync.ts`).

**Residual risk:** Some repository configuration cannot be neutralized by environment overrides and can still execute or redirect host git: driver-keyed configuration selected by repository content (`filter.<d>.*`, `diff.<d>.textconv`, `merge.<d>.driver`), `diff.external`, `tar.<format>.command`, `trailer.<token>.cmd`, `core.worktree` and gitfile/`commondir` redirects, `include.path`/`includeIf` content, `objects/info/alternates`, URL-scoped `http.<url>.*` settings and `url.<base>.insteadOf` rewrites. srt and the policy escalations are the controls (`inspectRepoConfig` in `src/security/git-hardening.ts` flags each of these); the inspection is defense in depth and racy against an agent that rewrites the repository meanwhile. It looks for symbolic links among the git directory's own entries, below `refs/`, `logs/` and git's state directories (`info`, `worktrees`, `rebase-merge`, `rebase-apply`, `sequencer`, `rr-cache`) and directly in `objects/`, not inside submodule git directories (`.git/modules`) or the git-lfs store, and escalates a git directory with more entries there than it walks (50,000). The agent can rewrite `.git/config` between evaluation and the git server's read, and conditional includes (`includeIf`) in the user's global git config are not evaluated. With `--workspace`, hooks and configuration the agent plants in the user's real repository persist and run on the user's later git commands: inspect `.git/hooks` and `.git/config` after untrusted sessions, or work in a fresh clone. In Docker Agent Mode the agent writes `.git` through the bind mount directly; the `.git` escalation covers Code Mode only. A compromised MCP server with the forwarded agent socket can authenticate as the user to any host the user's keys reach.

## 12. Supply Chain Attacks

**Risk:** Supply chain attacks affect the IronCurtain host process (npm dependencies run with full user privileges and bypass every sandbox), the images and servers it starts, and packages the agent installs inside containers.
**Mitigation:**

- **Host dependencies:** the repository lockfile (`package-lock.json`) fixes what developers, CI and the release build install and test, but it is not published: the package ships no lockfile or shrinkwrap, so `npm install -g @provos/ironcurtain` resolves the dependency ranges of `package.json` at install time (`docs/designs/dependency-hygiene.md`). `@anthropic-ai/sandbox-runtime` (`^0.0.77`, which npm resolves to that one version), `isolated-vm`, the filesystem MCP server and the git MCP server are pinned exactly.
- **npm audit gate:** `npm run check:audit` (`scripts/check-npm-audit.ts`) fails on any high or critical advisory in the production tree that the reviewed allowlist (`.github/npm-audit-allowlist.json`) does not accept. It runs in CI, weekly and in the release build, so no release is built while the locked production tree has a high or critical advisory nobody reviewed. An allowlist entry accepts named advisories in one package at their reviewed severity, says why that is acceptable here and expires at most 180 days after its review; an expired entry or a raised severity fails the gate again.
- **Install scripts:** npm 11.19 and later honor the root `package.json`'s explicit `allowScripts` decisions for project installs: `isolated-vm` and `node-pty` may build; scripts of packages mapped to `false` are skipped. A dependency with no entry still runs its lifecycle scripts, with a notice, unless `strict-allow-scripts` is enabled. The repository does not enable strict mode: ordinary developer `npm install` and CI `npm ci --foreground-scripts` use this warn-and-run behavior. `test/dependency-hygiene.test.ts` checks scripts in the already installed tree; it can report an unreviewed script only after installation, and does not prevent its execution. npm ignores the project field for a global install, so an end user whose npm configuration blocks unreviewed scripts allows the two required native modules with `npm install -g @provos/ironcurtain --allow-scripts=isolated-vm,node-pty`.
- **Release pipeline:** no release job that runs dependency, build or test code holds a publish or write credential; publishing verifies the tarball's checksum and uses npm trusted publishing with provenance (`.github/workflows/release.yml`). The committed build-trust binaries must rebuild byte-identically with the recorded toolchain (`docker/build-trust-runtime/`).
- **MCP server upgrades:** the MCP server packages are updated in their own Dependabot group with a re-annotation checklist (`.github/dependabot.yml`), and live schema drift is reported (§3).
- **Images and agent CLIs:** the `github` MCP server image is pinned by digest (`src/config/mcp-servers.json`); the macOS transport sidecar is built locally and run by immutable ID (`src/docker/transport-sidecar-image.ts`); agent CLIs are pinned to tested versions with a documented override (`src/docker/agent-cli-version.ts`); the memory server downloads only pinned, hash-verified models (`packages/memory-mcp-server/src/models/`).
- **Container level:** the registry proxy and its age gate (§2b-ii).

**Residual risk:** An installed copy resolves its dependency ranges when it is installed, so a dependency release published after an IronCurtain release, a compromised one included, reaches users without passing the audit gate or the test suite. Unless the user's npm configuration blocks unreviewed install scripts, a global install also runs the install script of every dependency that has one. Developer and CI installs also execute dependency lifecycle scripts absent from `allowScripts` before the hygiene tests can flag them; the committed decisions are not a deny-by-default install policy. A compromised build dependency can still alter the packed tarball, and provenance attests it faithfully. The build-trust check proves the committed binaries rebuild from their recorded toolchain; it does not pin them at run time. Doctor's package-asset checks (`readPackageAsset` in `src/hardened-fs.ts`) keep other local users from changing reviewed manifests, but they are a sanity check, not tamper-proofing: every principal they accept can change the code itself. Two `zod` 3 copies (under `@utcp/sdk` and sandbox-runtime) have no fix in range, and the reachable `undici` advisories let a malicious web server crash the fetch server process (`.github/npm-audit-allowlist.json`). Agent base images are pinned by tag, not digest. The default Signal bridge is an explicitly built local derived image with pinned upstream source, runtime and Go builder inputs (`docker/signal-bridge/README.md`). Custom images require authentication contract label `1`; a malicious publisher can apply that label, so admitting an image remains a trust decision (`src/signal/signal-image.ts`).

## 13. Memory Poisoning

Host memory review/show prints the complete quoted releasable payload, including tags, source label, metadata and source passage, with an `<id>@<digest>` receipt. Approval checks that snapshot in an IMMEDIATE database transaction; a changed row needs review again. Bare-id and bulk-all approval are unavailable, so an unseen row is never implicitly included (RV-08).

**Risk:** Persistent memory (`packages/memory-mcp-server/`) carries notes from one session into later ones. A note planted by an injected session reaches every later session of the namespace as context.
**Scope:** memory is on only for persona and cron-job sessions (`src/memory/memory-policy.ts`): a persona's database is shared by its interactive sessions, cron jobs and per-state workflow sessions; a job without a persona has its own (`src/memory/resolve-memory-path.ts`). Shared-container workflow bundles run no memory server.
**Mitigation:**

- **Provenance:** every memory records its writer kind (`interactive`, `cron`, `workflow`) and session (`MEMORY_WRITER_KIND`, `MEMORY_SESSION_ID`, set by `src/memory/memory-annotations.ts`).
- **Quarantine of unattended writes:** memories written by cron jobs and workflow states wait for review; interactive sessions do not see them or their source passages until they are approved with `ironcurtain memory <persona|job> review approve` (`src/memory/memory-command.ts`). The writing job's later runs (or the run's later states) see them.
- **Framing:** all memory output is wrapped as notes from earlier sessions that are data, not instructions (`packages/memory-mcp-server/src/utils/framing.ts`).
- **Bounded influence:** stored importance is capped at 0.8; secrets are rejected by `memory_store` and removed by `memory_ingest` (`packages/memory-mcp-server/src/utils/secrets.ts`).
- **Human-only bulk operations:** `memory_forget` by tags, query or date, or of more than 10 ids, and `memory_ingest` of more than 10,000 characters escalate to a human (`src/trusted-process/trusted-server-policy.ts`).
- **Recoverable deletes:** a database snapshot (0600, newest 5 kept) is taken before deletions (`packages/memory-mcp-server/src/storage/database.ts`).
- **Bounded memory LLM spend:** 500 LLM calls or 1,000,000 tokens per memory server process by default (`packages/memory-mcp-server/src/config.ts`).

**Residual risk:** Framing is prompt-level. Approving one fact also exposes its whole source passage. Rows written before quarantine existed are not quarantined. Up to 10 memories per call can be deleted by id without a human. Forget removes a fact's source passage and superseded copies, but forget snapshots keep deleted memories on disk until they rotate out, and compaction summaries written before the forget keep what they summarized. The memory server's LLM spend is outside the session budgets. A host paired with an older memory server that ignores the review scope gives no quarantine.

## 14. Workflows and Cron Jobs

**Risk:** Multi-agent workflows (`src/workflow/`) pass work between agents, run deterministic commands and can share containers; cron jobs (`src/cron/`) run agents unattended. Each agent's output is untrusted input for whatever reads it next.
**Threat model and controls:**

- **Cross-agent artifacts:** artifacts, transcripts and workspace files written by one state are read by later states, by deterministic steps and by the agent deciders of agent-driven gates. Treat them as untrusted; a prompt-injected state can try to steer every later one through them. Host-side walks and reads of the agent-written `.workflow/` tree never follow symlinks, never block on FIFOs and are bounded; a symlinked output counts as missing (`src/workflow/artifacts.ts`, `src/hardened-fs.ts`). On Linux an opened file is re-checked through `/proc/self/fd`; macOS falls back to re-resolving the path and comparing device and inode, which is weaker.
- **Dependency layers:** workflow runtime dependencies come from a shared base that is built in a short-lived provisioning container (no workspace, no agent session, no provider credentials) and never mounted into an agent container; each run gets its own writable copy (`src/docker/workflow-dependency-cache.ts`). A run's agents can still tamper with that run's own layer, and so with what its deterministic steps execute.
- **A container scope is one trust domain:** in shared-container mode every state of a `containerScope` shares processes, agent-CLI state and the scope's MCP proxy socket, so validation requires one persona per scope unless the workflow sets `settings.allowMixedPersonas: true`, which declares the scope a single trust domain (`src/workflow/validate.ts`). The workspace is shared by every state in every mode.
- **Fan-out lanes** in one scope share a trust domain too. `workflow_commit` is bound to one open invocation: stale processes and other states cannot commit another invocation's result, but a lane that reads another lane's transcript in the shared container could (`src/workflow/workflow-commit.ts`).
- **Least-privilege reviewers:** `workspaceAccess: read-only` states get a read-only workspace mount and write only their declared outputs through the filesystem server, which the policy engine confines to them (`src/workflow/workspace-access.ts`).
- **Host deterministic states** (`host: true`) execute agent-writable workspace code as the host user, with the user's environment and network, outside the container and the policy engine. They need an explicit per-state acknowledgement, are re-checked at runtime and run bounded (argv only, own process group, killed on timeout or abort, `src/workflow/host-command-runner.ts`). A process that calls `setsid` escapes the group kill. `container: true` is the contained alternative.
- **Escalations and gates:** workflow tool-call escalations reach a human with the configured timeout; auto-approval is off for workflows. Gate decisions are bound to a single raise (`src/workflow/gate-binding.ts`); an agent decider reads artifacts written by sandboxed agents and can itself be prompt-injected. Browser gate Approve requires 750 ms with the same complete review, visible focus and stable placement; interruption or movement invalidates held presses. This is client accidental-input hardening, not a new authorization channel (RV-21).
- **Budgets:** §9 (`settings.workflowBudget`). Terminal checkpoints retain the metrics subscription through session/proxy teardown and include settled charges. Provisional checkpoints mark usage incomplete; resuming them with token/cost ceilings fails closed.
- **Snapshot ownership:** external run bases cannot sweep or retire ownerless legacy images. Labelled images must match the base-directory owner key and run; only this home's own workflow-runs directory retains legacy compatibility.
- **Input staging:** `workflow run-state --artifacts` copies only regular files and real directories within shared entry/depth/byte limits, skipping links and special entries. The explicitly selected `--workspace` project layer retains ordinary project-copy behavior.
- **Imported runs:** an imported run directory may have been written by an agent, so imports re-check the definition (host commands need `--trust`), validate the workspace and refuse paths outside the imported run (`src/workflow/workflow-manager.ts`). A cross-process run lock prevents two processes from executing one run (`src/workflow/run-lock.ts`).
- **Cron jobs** run only under their own compiled policy (§1, `src/cron/job-policy.ts`). Their escalations go to Signal when the job notifies and Signal is configured, otherwise to the web UI while a browser is connected, and are denied at once when nobody can be asked (`src/daemon/ironcurtain-daemon.ts`). The job workspace's `.git` is rebuilt from a daemon-owned mirror before every run (§11), and the run summary the agent writes (`last-run.md`) is read without following links, bounded and sanitized (`src/cron/run-summary.ts`).

**Residual risk:** `resolvedBy` on gate decisions is declared by the caller, because the web UI bearer token is shared. There is no human-only gate flag yet. The cron git sync assumes no agent runs in the workspace during the sync (`src/cron/git-sync.ts`).

## 15. Web UI, Daemon and Remote Approval Channels

**Risk:** The daemon exposes control surfaces that can start agents and approve escalations.
**Web UI** (`src/web-ui/web-ui-server.ts`, opt-in `ironcurtain daemon --web-ui`):

- **Token powers:** one random bearer token per daemon start authorizes every JSON-RPC method: creating, resuming and ending sessions, sending messages and terminal input, approving escalations and gates, starting, importing, resuming and aborting workflows, running, enabling, disabling, recompiling and removing jobs, creating, deleting and editing personas (constitutions, memory and broad-policy opt-ins included), and changing model providers, budgets and nested-Docker settings (`src/web-ui/dispatch/`). Anyone holding it acts as the user.
- **Exposure:** the server binds 127.0.0.1 by default; the token travels in the URL (`?token=`) and in `~/.ironcurtain/web-ui.json` (mode 0600, for `ironcurtain observe`; `src/daemon/ironcurtain-daemon.ts`).
- **Hardening:** the Host header must name localhost, a loopback address, the configured bind host or (with a wildcard bind) an IP literal, otherwise 421; WebSocket handshakes with a foreign Origin are refused (dev mode only adds the Vite origin); responses carry a strict Content-Security-Policy, `Referrer-Policy: no-referrer` and `X-Frame-Options: DENY` (`src/web-ui/web-ui-server.ts`).
- **Daemon resource safety:** workflow file and artifact reads never follow links or block on FIFOs and are size-bounded (`src/web-ui/dispatch/workflow-dispatch.ts`), and an oversized reply becomes a `RESPONSE_TOO_LARGE` error instead of a closed socket (`src/web-ui/web-ui-server.ts`); terminal sizes are bounded by the RPC schema and clamped again before the headless terminal allocates them (`src/pty/pty-size.ts`); an approval that arrives after an escalation expired is reported as `ESCALATION_EXPIRED`, never as a success (`src/web-ui/dispatch/escalation-dispatch.ts`).

**Daemon control socket:** `~/.ironcurtain/daemon.sock` is created 0600 in a 0700 directory, requests are schema-validated and capped at 1 MiB, and filesystem permissions are the only access control (`src/daemon/control-socket.ts`).

**Signal:** every `memory_forget` selector and `memory_ingest` argument must fit the complete review; oversized memory requests are deny-only, including after details. Approvals over Signal must quote a per-escalation code the agent cannot learn, and banners cannot be styled by agent text (`src/signal/escalation-reply.ts`). The signal-cli bridge container holds the bot's keys and is trusted for every inbound message and identity answer; its image is resolved to an immutable ID and must carry authentication contract label `1` (§12). Setup, health, registration, identity, send and receive use the same CA-pinned HTTPS/WSS client with bearer admission, without redirects or plaintext fallback.

**Terminal output:** relay diagnostics are bounded and rendered as inert single-line text, including forwarded list-resolution warnings. Startup stderr capture is capped at 64 Ki characters; overflow drops the entire sample before credential redaction so a cut secret prefix is not displayed (RV-06). Developer tool discovery uses the shared sandbox/credential launcher, including configured extra protected paths (RV-14). Agent-derived text shown on the user's terminal, in the workflow and job CLIs and in `ironcurtain observe`, is sanitized (`src/terminal/display-sanitize.ts`, `src/observe/observe-text.ts`); raw `start --pty` and Apple native exec output passes a stateful filter that forwards printable text and allowlisted sequences only and drops OSC 52 (clipboard), OSC 8, titles and text-echoing reports (`src/terminal/terminal-output-filter.ts`). Terminal agent Markdown shows literal link/image destinations as inert escaped text. Keyless CLI JSON sinks escape terminal-active and invisible characters without changing decoded values; workflow watch also normalizes harmless JSON whitespace outside strings. Persisted audit and workflow evidence is unchanged (RV-12/RV-23).

**Residual risk:** The web UI token appears in URLs and browser history. Local users who can reach the loopback port still need the token. The Signal bridge also remains network-reachable, but enforces TLS and bearer admission on every HTTP route and WebSocket upgrade, including its container address. The separate JSON-RPC daemon binds only container loopback. Its token, certificate and key are one atomic mode-0600 file under `oauth/signal-bridge/` (directory 0700), mounted read-only; bundle fingerprints bind container reuse to the current credentials. Foreign-owned or mismatched-data containers are refused untouched. An owned legacy listener is removed before replacement-image admission, so an unavailable replacement cannot leave it running. Docker administrators, the owner and a compromised bridge retain access to the bot's keys and message stream. Actual macOS Docker Desktop/Apple runtime and live Signal account qualification remain owner work; see `docs/designs/signal-transport.md`.
